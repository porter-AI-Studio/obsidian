核心概念

Vault 保管庫 第 01 章第 02 章

Obsidian 中的資料存放區域，集中管理所有筆記與設定。

Vault 是一個獨立的資料夾，包含所有筆記、連結、附件以及設定檔（.obsidian/）。使用者可在不同 Vault 間切換，隔離專案或主題；同時，它也是插件與同步功能的基礎。每個 Vault 都是一個完全獨立的單元，可以搬移到任何位置而不影響內部連結。

提示：開啟新 Vault 前先備份舊資料；若要跨裝置同步，選擇一種同步方案（iCloud / Remotely Save / Obsidian Sync）後就不要混用，以免產生衝突。
Wikilink 雙向連結語法 第 04 章第 05 章第 06 章

以 [[筆記名稱]] 標記、建立筆記間雙向連結的核心語法。

雙向連結允許筆記互相指向對方，使用 [[標題]] 語法即可。它不僅建立正向鏈接，同時自動產生反向索引（Backlink），方便在不同主題間追蹤關係。在 Graph View 中，Wikilink 數量越多的筆記，節點越大、連線越密，可直觀顯示整體知識網絡結構。

提示：必須使用雙括號，單括號 [文字](URL) 是 Markdown 外部連結，不會建立 Backlink；[[筆記名#標題]] 可精確指向筆記內的某個段落。
Backlink 反向連結 第 04 章第 05 章

由其他筆記引用而自動產生、顯示在當前筆記的「誰連到我」列表。

當你在筆記 A 裡寫 [[筆記B]]，筆記 B 的側欄就會自動出現一條 Backlink，顯示「筆記 A 連結了你」。這個機制讓你不需要事先計劃連結方向——先寫，連結自然形成。Backlink 是 Obsidian 區別於傳統資料夾系統最核心的優勢之一。

提示：在右側欄開啟「Backlinks」面板，即可看到所有引用當前筆記的連結。Backlink 是發現意外關聯的最佳工具。
Block Reference 區塊引用 第 04 章

引用另一筆記中特定段落（區塊）並保持同步顯示的精確連結語法。

使用 [[筆記名稱#^block-id]] 可精確引用某個段落，而非整篇筆記。被引用的區塊會在目標筆記自動加上 ^block-id 標記。嵌入顯示時使用 ![[筆記#^block-id]]，內容會即時渲染在當前頁面。適合在 MOC 頁面聚合多份筆記的重點摘要。

提示：不要手動修改 ^block-id，否則引用會失效；Obsidian 在你輸入 ^ 時會自動提示可引用的區塊。
Graph View 關聯圖 第 05 章

以節點與連線視覺化所有筆記之間連結關係的互動式全域圖。

按 Ctrl+G（Windows）或 Cmd+G（Mac）開啟全域關聯圖，每個筆記是一個節點，每條 Wikilink 是一條線。節點大小反映被連結的次數，顏色可按標籤分組。Graph View 最大的用途是發現「孤島筆記」（沒有任何連結的筆記）和「樞紐筆記」（被大量引用的核心概念）。

提示：不要在 Graph View 資訊過多時就全開——善用左側篩選條件，按標籤或資料夾縮小範圍，才能看清楚結構。Graph View 是診斷工具，不是日常工作介面。
Local Graph 區域關聯圖 第 05 章

只顯示當前筆記及其直接相連筆記的小範圍關聯圖。

與全域 Graph View 不同，Local Graph 聚焦於「這篇筆記的鄰居」，包含它連出去的筆記與連進來的 Backlink。在筆記右鍵選單或命令面板中可開啟。深度（depth）設定為 2 時，還會顯示鄰居的鄰居，方便發現二度連結的概念關聯。

提示：Local Graph depth 設 1 到 2 最清晰；設太高（4 以上）會載入全庫，失去「區域」意義。

Metadata 系統

Frontmatter 前置屬性 / YAML 區塊 第 06 章

筆記最上方以三個連字符（---）包圍的 YAML 格式元資料區塊。

Frontmatter 位於筆記第一行，以 --- 開始和結束。裡面可放任意鍵值對，例如 title、tags、created、status 等。Obsidian 的 Properties 面板會自動解析並以圖形化介面呈現這些欄位，Dataview 查詢也以 Frontmatter 欄位作為篩選條件。

提示：YAML 對縮排非常敏感，錯誤的縮排會讓整個 Frontmatter 解析失敗。建議用 Properties 面板編輯，而非直接手寫 YAML。
Properties 屬性面板 第 06 章

Obsidian 1.4+ 提供的圖形化介面，用於檢視與編輯筆記的 Frontmatter 欄位。

Properties 面板顯示於筆記上方，自動解析 Frontmatter 的 YAML 並以欄位形式呈現。支援文字、日期、多選、Checkbox 等多種欄位類型。點擊「+」新增欄位，Obsidian 會記憶你用過的欄位名稱並在輸入時自動補全，保持全庫欄位名稱一致性。

提示：在設定 → 編輯器中可選擇「在來源模式下隱藏 Properties」，如果你習慣直接寫 YAML 可關閉圖形化顯示。
Tag 標籤 第 06 章第 09 章

以 #標籤名 標記的關鍵詞，可跨資料夾將相關筆記聚合在一起。

Tag 不受資料夾結構限制，一篇筆記可以同時有多個標籤。支援層級結構：#書/非小說 是 #書 的子標籤。在 Graph View 中可按標籤著色，在 Dataview 中用 FROM #標籤 查詢所有帶此標籤的筆記。Tag 最適合描述「類型」（什麼類的東西），資料夾最適合描述「歸屬」（屬於哪個專案）。

提示：Tag 和資料夾不是競爭關係，應互補使用。常見錯誤：所有東西都丟進 #general 或 #todo，失去分類意義。

工作流方法論

Daily Notes 每日筆記 第 07 章

以當天日期為標題自動產生的筆記，作為每日資訊捕捉與反思的起點。

在 Core Plugins 啟用「Daily Notes」後，每天開啟 Obsidian 時可一鍵建立以日期命名（如 2026-06-20.md）的筆記。搭配模板（Template 或 Templater）可預填結構：三件重要的事、會議記錄、靈感、反思。Daily Notes 是 LYT 系統的「流」，MOC 則是「固化」的結晶。

提示：Daily Notes 不是日記，是工作流的捕捉層。不要讓它無限堆積——定期將重要內容「蒸餾」到主題筆記，Daily Notes 本身可以歸檔或刪除。
MOC (Map of Content) 內容地圖 第 07 章

一種聚合相關筆記連結的索引頁，作為某個主題的導覽起點。

MOC 本身是一篇普通的 Markdown 筆記，內容是一系列 Wikilink 的集合，指向該主題下所有相關筆記。它不是資料夾，所以一篇筆記可以出現在多個 MOC 裡。MOC 的典型結構：頂層主題 MOC → 子主題 MOC → 具體筆記。在 LYT 系統中，MOC 是知識「結晶」的地方，把 Daily Notes 的碎片整理成有結構的知識地圖。

提示：MOC 是活的文件，應該持續更新。不要把 MOC 當成靜態目錄，它應該反映你當前對這個主題的理解結構。
PARA PARA 知識組織系統 第 03 章

由 Tiago Forte 提出的四層知識組織框架：Projects（專案）、Areas（領域）、Resources（資源）、Archives（歸檔）。

PARA 把所有資訊按「時效性」分層：Projects 是有截止日期的事項，Areas 是需要持續維護的生活領域，Resources 是可能某天用到的主題參考，Archives 是完成或停用的項目。四個資料夾對應四種思維模式，讓你在「我現在要做什麼」和「我積累了什麼知識」之間清晰切換。

提示：PARA 的核心是「行動導向」——把資訊按照「對當前行動的距離」分類，而非按學科分類。最常見的錯誤是把所有東西丟進 Resources，讓它變成另一個垃圾桶。
LYT (Linking Your Thinking) 連結你的思考 第 07 章

由 Nick Milo 提出的筆記方法論，以 MOC 為核心、用連結組織知識取代資料夾結構。

LYT 強調「思考是連結的行為」，筆記的價值不在於它本身，而在於它與其他筆記的關係。核心工具是 MOC（Map of Content）——建立主題索引頁，讓筆記按概念關聯聚合，而非按資料夾物理位置分隔。LYT 與 PARA 可以共存：PARA 管理專案行動，LYT 管理概念知識。

提示：LYT 的學習曲線在於「習慣在寫筆記時思考它和什麼有關」。從 Inbox 開始，每週花 30 分鐘把 Inbox 的筆記連結到現有的 MOC，就是實踐 LYT 的起點。
C.O.D.E 知識流程四步驟 第 03 章

Tiago Forte 提出的知識流程：Capture（捕捉）→ Organize（組織）→ Distill（提煉）→ Express（表達）。

C.O.D.E 是建立第二大腦的四個動作循環。Capture 是「凡值得留存的都記下來」；Organize 是「按 PARA 放到對的地方」；Distill 是「去掉雜訊，留下精華」（加粗、摘要）；Express 是「把知識變成輸出物」（文章、報告、決策）。四步驟是一個循環，不是單向線性流程。

提示：最常被跳過的是 Distill——很多人 Capture 之後就不再動那份筆記。試著在每次重讀筆記時，加一句「對我最重要的是：⋯⋯」，這就是 Distill 的起步。
Second Brain 第二大腦 第 03 章第 14 章

將個人知識外化到數位工具中，形成可搜尋、可連結、持續成長的個人知識管理系統。

「第二大腦」這個概念由 Tiago Forte 推廣，核心主張是：人的工作記憶有限，把「知道什麼」這件事外包給可靠的筆記系統，讓大腦專注在「思考與決策」。在 Obsidian 的語境下，Second Brain = Vault + 連結結構 + 定期回顧習慣 + AI 整合工作流。

提示：Second Brain 的目標不是「記住更多」，而是「需要時能找到」。不要讓筆記系統成為囤積資訊的倉庫——持續 Distill 和 Express 才讓系統有生命力。

核心插件

Dataview Dataview 插件 第 09 章

將 Obsidian 筆記的 Frontmatter 欄位當作資料庫，用類 SQL 語法動態查詢並呈現結果的社群插件。

安裝後可在筆記中嵌入 dataview 程式碼區塊，執行 LIST、TABLE、TASK 等查詢。例如 TABLE status FROM #project WHERE status = "進行中" 會即時列出所有進行中的專案筆記。Dataview 查詢是即時的——筆記內容一更新，查詢結果自動重新計算，不需要手動維護清單。

提示：Dataview 查詢語法大小寫不敏感，但欄位名稱需與 Frontmatter 完全一致（包含大小寫和底線）。大型 Vault 中複雜查詢可能影響效能，建議限縮查詢範圍（加 FROM 條件）。
Templater Templater 插件 第 10 章

比 Obsidian 原生 Templates 更強大的模板插件，支援 JavaScript 運算、日期函式和使用者輸入提示。

Templater 使用 <% %> 標記嵌入動態內容：<% tp.date.now('YYYY-MM-DD') %> 插入當天日期，<% await tp.system.prompt('輸入標題') %> 在建立筆記時彈出對話框。與原生 Templates 相比，Templater 支援條件判斷、迴圈，甚至可以呼叫外部 API。配合「Folder Templates」設定，在特定資料夾建立新筆記時自動套用對應模板。

提示：啟用「Trigger Templater on new file creation」讓新筆記自動套用模板；需要在設定中開啟「Enable JavaScript modules」才能使用完整的 JS 功能。
Obsidian Web Clipper 網頁剪藏工具 第 12 章第 13 章

官方推出的瀏覽器擴充功能，一鍵將網頁內容轉換為 Markdown 並存入 Vault。

安裝瀏覽器擴充後，瀏覽任何網頁時點擊圖示即可剪藏。支援自訂模板（Template）定義剪藏格式，使用 {{title}}、{{url}}、{{content}} 等變數自動填入。進階版支援 {{ai:...}} 語法，讓 AI 在剪藏時自動生成摘要或推斷標籤。所有剪藏內容儲存在本地 Vault，不依賴任何雲端服務。

提示：在 Clipper 設定中設定「預設目標資料夾」（如 Clippings/），搭配 Templater 自動加上 Frontmatter，讓剪藏筆記從一開始就有結構。
Custom Attachment Location Custom Attachment Location 插件 第 11 章

讓每篇筆記的附件自動存入同名子資料夾，並在筆記重新命名或移動時自動更新路徑的社群插件。

設定路徑規則為 ./assets/${filename}/ 後，貼上圖片時會自動存到 assets/筆記名/ 目錄。筆記改名時，附件目錄跟著改名；筆記移動時，附件跟著搬移。還提供「批次整理」功能，對全庫現有附件一鍵套用新規則。這解決了 Obsidian 原生設定「移動筆記後連結斷掉」的根本問題。

提示：安裝後先在命令面板執行 Custom Attachment Location: Reorganize 前，務必先備份整個 Vault——批次移動是不可逆操作。
Image Converter Image Converter 插件 第 11 章

貼上圖片時自動壓縮並轉換格式（通常為 WebP），縮小 Vault 體積的社群插件。

啟用後，截圖貼入筆記時自動轉成 WebP 格式，體積縮小約 70~80%。支援格式統一（全庫圖片統一成同一格式）、自動以筆記名 + 序號重命名（如 專案計劃-1.webp），以及 Ctrl + 滾輪縮放圖片預覽大小。此插件涵蓋了 Paste Image Rename 的所有功能，若只能裝一個圖片相關插件，選它。

提示：若 Vault 要同步到行動裝置，WebP 格式在 iOS 的 Obsidian App 完整支援，不需要擔心相容性問題。

同步方案

Remotely Save Remotely Save 插件 第 17 章

支援多種雲端後端（WebDAV、S3、Dropbox）的免費同步插件，是官方 Obsidian Sync 的免費替代方案。

支援的後端包含 WebDAV（堅果雲、自建 NAS）、Amazon S3、Cloudflare R2、Dropbox、OneDrive。對台灣用戶最推薦的組合是「堅果雲 WebDAV」——堅果雲提供免費 WebDAV 存取，搭配 Remotely Save 可在 iOS、Android、電腦三端同步。設定完成後點「立即同步」，之後每次開啟 Obsidian 自動觸發同步。

提示：堅果雲的 WebDAV 密碼需在官網「帳號設定 → 安全設定 → 第三方應用管理」另行產生，不是登入密碼。第一次同步前確認「測試連線」成功再繼續。
Obsidian Git Obsidian Git 插件 第 17 章

把 Vault 當作 Git Repository 管理，自動定時 commit + push 的版本控制插件。

安裝後在設定中指定 Git Repository 路徑與遠端（通常是 GitHub Private Repo），設定 auto pull 和 auto push 的間隔（建議 10 分鐘）。每次自動 push 都有完整的 commit 歷史，誤刪筆記可隨時復原。Commit 訊息支援 {{date}} 變數自動帶入時間戳。Obsidian Git 最適合電腦端使用，iOS 端因 App Store 政策限制幾乎不可行。

提示：建議把 .obsidian/workspace.json 加入 .gitignore，這個檔案記錄視窗狀態，頻繁變動會汙染 commit 歷史。
Syncthing Syncthing 第 17 章

基於 P2P 協議的開源同步工具，裝置間直接傳輸檔案，不經過任何雲端伺服器。

在兩台裝置都安裝 Syncthing 客戶端後，透過裝置 ID 互相授權，即可建立加密的直接同步連線。區域網路下速度接近滿速，遠比雲端方案快。不需要任何訂閱費或第三方帳號，資料從不離開你掌控的設備。適合「公司電腦 ↔ 家用電腦」或「電腦 ↔ Android」的同步場景；iOS 端需購買 MobiusSync（約 $7 美元，一次性付費）。

提示：Syncthing 需要兩台裝置同時開機才能同步，無法像雲端方案一樣非同步。若有「隨時在任何裝置取得最新筆記」的需求，考慮搭配 Remotely Save 補強。
Obsidian Sync Obsidian 官方同步服務 第 17 章

Obsidian 官方推出的端到端加密跨裝置同步服務，年繳約 $4 美元/月起（月繳約 $5 美元/月，2026-09-03 查證 obsidian.md/pricing），零配置、所有設定一起同步。

官方 Sync 支援最多 10 台裝置，同步範圍包含筆記、插件設定、主題、Hotkey——這是它與第三方方案最大的差異，其他方案通常只同步筆記內容，不同步 Obsidian 的 UI 配置。端到端加密意味著 Obsidian 的伺服器也無法讀取你的資料。對不想折騰技術設定、重度 iOS 使用者或知識工作者來說，這是最直接的選擇。

提示：官方 Sync 與第三方雲端硬碟（iCloud、Dropbox）不相容，啟用後不要把 Vault 放在 iCloud 資料夾，否則兩者會衝突造成資料損毀。

CLAUDE.md Claude 指令設定檔 第 14 章第 16 章

放在 Vault 根目錄的 Markdown 設定檔，用於告訴 Claude Code 如何處理這個 Vault 的筆記。

當你在 Vault 目錄執行 claude 指令時，Claude Code 會自動讀取 CLAUDE.md 作為上下文指令。你可以在裡面定義：資料夾結構說明、筆記命名規則、不可修改的目錄（如 Archive/）、常用 Prompt 模板等。這讓 Claude 在操作 Vault 時有清楚的行為邊界，避免誤刪或誤改重要筆記。CLAUDE.md 是整個 AI 工作流的基石——在 AI 整合之前，先寫好它。

提示：在 CLAUDE.md 中明確列出「不要修改的資料夾」和「不要刪除的檔案」，這是最重要的安全護欄。特別是 Archive/、Daily/ 這類重要目錄。
LLM Wiki LLM Wiki 知識庫 第 16 章

由 AI（LLM）自動整理與維護的 Markdown 知識庫，隨每次查詢持續累積內容。

由 Andrej Karpathy 推廣的方法：將原始文章投入 raw/ 資料夾，AI 自動拆解概念、更新 wiki/Concepts/、wiki/Entities/ 等結構化頁面。每次向 AI 提問，AI 不只回答，還把答案存回 Wiki——「知識隨查詢累積」。這套方法的核心洞見是：**LLM 的 Context Window 大到足以維護一個中型 Wiki，不需要 RAG**（適用於 100 篇左右的知識庫規模）。

提示：LLM Wiki 適合 100 篇以內的知識庫。超過這個規模，每次查詢的 token 成本會線性增長，此時應考慮引入向量搜尋（RAG）架構。
Ingest 知識攝取（Ingest） 第 16 章

將外部原始資料（文章、網頁、影片字幕）投入知識庫並由 AI 整理成結構化筆記的動作。

在 LLM Wiki 工作流中，Ingest 是第一步：把原始資料丟進 raw/ 資料夾，呼叫 AI Skill（如 /ingest-url <網址>），AI 自動擷取內容、拆解概念、更新對應的 Wiki 頁面。Ingest 的本質是「編譯」——把人類語言的資訊轉換成結構化知識，而不是單純的複製貼上。**提問本身也是一種 Ingest**：你問 AI 一個問題，AI 的回答存回 Wiki，下次同樣的問題就不需要再問。

提示：Ingest 後記得讓 AI 更新 wiki/index.md，否則下次查詢時 AI 找不到新增的知識節點。
Claude Code Claude Code（CC） 第 14 章第 15 章第 16 章

Anthropic 推出的 AI CLI 工具，在終端機以自然語言指令操作檔案系統、執行程式、管理 Vault。

在 Vault 目錄執行 claude 即進入互動模式，可用自然語言指令讓 Claude 讀取、建立、修改 Markdown 筆記，或執行自訂 Skills（/skill-name）。Claude Code 直接存取本地檔案系統，因此可以：批次整理 Frontmatter、建立 LLM Wiki 結構、每日自動生成週報、從影片字幕建立筆記等。與 Obsidian 的插件不同，Claude Code 在 Obsidian 外部運行，適合大批量處理和複雜自動化。

提示：Claude Code 在 Vault 目錄中使用時，會自動讀取 CLAUDE.md 作為上下文。先把 Vault 的規則和限制寫進 CLAUDE.md，讓 Claude 知道邊界，再開始讓它處理筆記。
