第 18 章 · Part 5：AI 整合：打造 AI 驅動的知識庫

任務與排程管理：讓 Obsidian 成為 AI Agent 的集中排程中心

三個 AI 工具、各自排程、沒人追蹤漏跑——用純檔案格式解決一個真實發生過的問題

問題意識：三個 AI Agent，各自的排程孤島

如果你和本書作者一樣，同時用 Claude Code、Codex、Antigravity 三個 AI Agent 工具排入未來要做的工作， 很快就會撞上一個尷尬的現實：這三個工具互不相通。 Claude Code 委派給 Codex 的任務、Antigravity 排入的排程、手動用 Windows 工作排程器建立的一次性續跑任務—— 分別散落在三個地方，沒有任何一處能讓你一眼看到「現在到底有哪些排程」「哪些已經完成」「哪些是週期性、哪些是一次性」。

更嚴重的問題不是「分散」，而是漏跑沒人發現。實際發生過的狀況是：排程因為電腦關機、 或 Claude Code 5 小時 session 使用限制而沒有真正跑完，事後也完全沒有機制回頭追蹤這些「漏跑」或 「跑到一半中斷」的工作——問題不會自動浮現在任何人眼前，只能靠人自己記得回去查，而人當然不會記得。

這不是假設情境：本章接下來會用今天實際做出來、已經在使用者機器上跑的系統示範。文中所有指令輸出、真實案例編號（如 SCH-0047、SCH-0048）、匯入筆數，都是實測結果，不是示意資料。

選型評估：為什麼沒有直接採用現成工具

在動手自建之前，先評估了幾個現成的開源方案是否能直接當後端使用——這一步很重要，能省下的工程量絕對優先於重造輪子。

候選工具 看起來合適的地方 實際卡住的地方
Taskwarrior 成熟、功能完整的命令列任務管理工具 Windows 無原生二進位，需要 WSL；資料是專有格式，要接 Obsidian 還得再寫一層 JSON → md 轉檔，工程量比自建更大
todo.txt 純文字、格式極簡 核心不支援週期性任務（要另裝外掛的外掛），一行純文字也對應不到 Bases 的 frontmatter 資料庫視圖
pueue 命令列任務佇列，看起來像「排程管理」 語意錯位——它排的是「真的會被執行的 shell 指令」，不是「工作紀錄」，也沒有 recurring / one-time 的概念
GitHub Issues 介面成熟、協作方便 需要網路，不是離線優先；recurring 也非原生概念；為了排程另開一個「非程式碼」語意的 repo，很奇怪

最後的結論是：不整套採用任何一個。改為自建「Markdown + YAML frontmatter + 一支 Python CLI」當骨幹， 用 Obsidian 內建的 Bases 當儀表板，再疊加安裝 Obsidian Tasks plugin（8.4.0） 當手動輸入的輔助層——這裡有一個值得留意的分寸拿捏：Bases 是骨幹儀表板，Tasks plugin 只是給人手動補記一筆的方便管道， 兩者職責不同、不衝突，也不是「用 A 取代 B」的關係。

為什麼還裝 Tasks plugin？ Tasks plugin 認的是 - [ ] checkbox 語法行，跟自建的 frontmatter 筆記完全是兩套機制，並存無礙。真正的資料骨幹（漏跑偵測、狀態機、CLI 操作）全部只靠 Markdown + YAML frontmatter，Tasks plugin 純粹是「懶得開 CLI 時，隨手記一筆」的入口。

認識 Obsidian Bases：內建的資料庫視圖

這是本章要教的一個全新知識點——本書 ch09 介紹過的 Dataview，需要額外安裝社群插件， 用 DQL（類 SQL 查詢語言）撰寫查詢；而 Bases 是 Obsidian 官方內建的資料庫式檢視功能， 不需要安裝任何外掛，直接在 Vault 裡建立一個 .base 檔案，就能用視覺化設定介面 （篩選、排序、分組、公式欄位）把一批帶有 frontmatter 的筆記變成表格、看板或卡片視圖。

比較項目 Dataview（ch09） Bases（本章新知識點）
安裝方式 需要安裝社群插件 Obsidian 內建，免安裝
操作方式 在筆記裡寫 DQL 查詢語法 在 .base 檔用 YAML 定義視圖，可搭配介面點選調整
呈現位置 嵌在某一則筆記的內容裡 獨立的檔案（.base），本身就是一個可切換的多視圖儀表板
公式欄位 DataviewJS 才能做複雜運算 內建 formulas，可直接用條件式衍生新欄位（如本章的 attention_reason）
適合場景 嵌入單則筆記的動態彙整（閱讀清單、MOC） 獨立儀表板、多視圖切換、需要分組與彙總的資料庫式檢視

本章的排程系統選 Bases 而非 Dataview 當儀表板，原因很直接：排程資料的每一筆本來就是結構化的 frontmatter， 不需要嵌在某則筆記正文裡查詢，而是需要一個獨立、可以切換好幾個視圖（全部總覽 / 只看異常 / 只看週期性）的 儀表板頁面——這正是 Bases 的原生定位。實際檔案是 schedule-log.base，打開就能看到 5 個 view， 不需要額外設定。

動手試試：完全用滑鼠點選做出一個儀表板，不必寫一行 YAML

本章展示的 schedule-log.base 是直接寫 YAML 檔案做出來的——因為它要被三個 AI 工具的自動化流程 共同維護，YAML 比較適合程式操作。但如果你只是想幫自己的個人任務、讀書清單、專案追蹤做一個儀表板， 完全不需要碰任何程式碼：Bases 內建的視覺化編輯介面就能做到本章示範的所有效果——篩選、排序、 分組、甚至公式欄位，全部用點選完成。

找不到「Bases」？在繁體中文介面裡它叫「資料庫」。 這是實測 Obsidian 指令面板（Ctrl/Cmd+P）查出來的真實指令清單，不是憑印象猜的：

指令 ID介面顯示名稱（繁體中文）
bases:new-file資料庫: 建立新的 base
bases:insert資料庫: 插入新的 base
bases:add-view資料庫: 添加檢視
bases:change-view資料庫: 變更檢視
bases:add-item資料庫: 添加項目
bases:copy-table資料庫: 複製表格到剪貼簿

也就是說：在指令面板打「base」英文可能搜不到，但打「資料庫」就能找到建立新 base 的指令——這是英文 功能名稱經過在地化翻譯後，中文使用者最容易卡住的第一步。

從零開始做一個屬於你自己的儀表板，流程是：

  1. 建立 base：在檔案總管對資料夾按右鍵，或用指令面板執行「資料庫: 建立新的 base」，Obsidian 會產生一個 .base 檔案並直接開啟編輯畫面。
  2. 選定範圍：畫面上設定這個 base 要涵蓋哪些筆記——可以指定資料夾、標籤，或任何 frontmatter 屬性當篩選條件，全部用下拉選單與點選完成，效果等同本章 YAML 裡的 filters 區塊。
  3. 加檢視（View）：用「資料庫: 添加檢視」或畫面上的加號，一個 base 可以並存多個檢視——表格、卡片、清單——分別代表本章「全部總覽」「⚠️ 需要人工介入」這種不同角度的視圖，讀者可以自己點出更多個。
  4. 排序與分組：每個檢視的欄位標題可以直接點擊切換排序方向；分組（groupBy）則是把某個屬性（例如 status）當成群組依據，畫面上會自動把同狀態的項目收在一起——效果等同本章「全部總覽」view 用 status 分組的做法，但完全用點選完成。
  5. 加公式欄位：在屬性清單裡新增一個「公式」型別的欄位，直接在欄位設定裡寫類似 if(...) 的條件式（Bases 有自己的簡易公式語法，比 DataviewJS 好懂很多）——本章 attention_reason 這種「依狀態自動產生一句話說明」的欄位，就是這樣做出來的。

重點是：從頭到尾不需要打開任何程式編輯器，也不需要安裝任何外掛。本章為了讓三個 AI 工具能一起 維護資料，選擇把最終結果寫成 YAML 檔案；但對讀者來說，Bases 存在的意義正是「用 Obsidian 原生的資料庫視圖， 取代你原本可能要開 Excel 或另外裝 Dataview 才能做到的事」。

系統設計：Markdown + YAML Frontmatter 骨幹

資料放在 Obsidian vault 裡一個獨立的資料夾 schedule-log/，底下只有兩個子資料夾： items/ 放進行中的項目，done/ 放已完成或已取消的項目。 每一筆工作項目是一個獨立的 Markdown 檔案，資料寫在 YAML frontmatter 裡—— 不是 JSON 資料庫，也不是一排 checkbox，而是「一則筆記就是一筆資料列」，剛好對應 Bases 的運作模型。

Frontmatter Schema 核心欄位

核心共通欄位：id（SCH-NNNN 流水號）、type（one_time 一次性 / recurring 週期性）、source_tool（標記排入這筆工作的是哪個工具：claude-code / codex / antigravity / manual）。以下是兩筆真實資料——本機機器上實際存在的項目：

items/SCH-0048-*.md（一次性，真實案例） 
---
id: SCH-0048
type: one_time
title: Codex-Resume-Claude-MicronYC（Windows 排程續跑 session）
source_tool: claude-code
executor: windows_task_scheduler
working_dir: C:\00tsc\MirconYC\Project_MicronYC
session_id: 6c17fc76-aebe-45b4-8194-6bcf0481bba2
resume_tool: claude
status: stalled
scheduled_for: '2026-08-19T12:40:00+08:00'
started_at: '2026-08-19T13:01:21+08:00'

rerun_count: 0

一次性項目的 status 有六種：pending / running / done / cancelled / missed / stalled；後兩種是本系統的核心賣點，下一節詳細說明。

items/SCH-0047-*.md（週期性，真實案例） 
---
id: SCH-0047
type: recurring
title: Herdr 整點打卡問候（gyro+porter）
source_tool: manual
executor: windows_task_scheduler
project: herdr
status: active
health: ok

interval_minutes: 20
tolerance_minutes: 15
last_run_at: '2026-09-03T10:00:30+08:00'
last_run_status: success
next_expected_at: '2026-09-03T10:20:30+08:00'
task_scheduler_name: Porter-Herdr-Claude-Hourly-Greeting
---

## 執行紀錄

| 時間 | 狀態 | 備註 |
|---|---|---|
| 2026-09-03T10:00:30+08:00 | success | targets=gyro,porter 全部成功 |
| 2026-09-03T09:40:01+08:00 | success | exit=0（來自 Windows Task Scheduler LastTaskResult） |

週期性項目的 status 是 active / paused / retired， 描述的是「這個週期性定義本身的生命週期」；每次真正執行則記在同一個檔案的 body 裡，用 Markdown 表格 append 一行執行紀錄（時間 / 狀態 / 備註），不是每次執行都新增一個檔案。 超過 500 行會自動歸檔到另一個檔案，避免單一檔案無限增長。

刻意對齊 Claude 的設計：max_running_minutes 預設值是 300 分鐘（5 小時），這不是隨便挑的數字，而是刻意對齊 Claude Code 的 5 小時 session 使用限制這個真實痛點——一個委派任務如果跑超過這個時間還沒結束，八成不是還在正常工作，而是卡住了。

核心機制：漏跑（missed）與中斷（stalled）自動偵測

這是整套系統存在的核心理由：光是把排程記錄下來還不夠，真正的價值在於自動抓出「本來該發生卻沒發生」的事。 判定邏輯很單純，但威力很大：

  • 一次性項目 missed：status=pending 且已經超過 scheduled_for + tolerance_minutes（排定時間到了、容忍值也過了，但根本沒開始執行）
  • 一次性項目 stalled：status=running 且已經超過 started_at + max_running_minutes（開始執行了，但跑超過 5 小時還沒結束）
  • 週期性項目 overdue：status=active 且已經超過 next_expected_at + tolerance_minutes（該執行的時間點過了，但沒有新的執行紀錄）

這個判定邏輯寫在 status.py 裡，以下是實際原始碼節錄——邏輯刻意寫得很直白，方便日後維護：

schedule-log/status.py（節錄） 
def derive_one_time_status(item, now=None) -> str:
    now = now or datetime.now(config.TZ)
    data = item.data
    status = data.get("status")
    if status in ("done", "cancelled"):
        return status
    if status == "pending":
        scheduled_for = _parse_dt(data.get("scheduled_for"))
        tolerance = int(data.get("tolerance_minutes") or config.DEFAULT_TOLERANCE_MINUTES)
        if scheduled_for and now > scheduled_for + timedelta(minutes=tolerance):
            return "missed"          # 排定時間 + 容忍值都過了還沒開始 → 漏跑
        return "pending"
    if status == "running":
        started_at = _parse_dt(data.get("started_at"))
        max_running = int(data.get("max_running_minutes") or config.DEFAULT_MAX_RUNNING_MINUTES)
        if started_at and now > started_at + timedelta(minutes=max_running):
            return "stalled"         # 跑超過 max_running_minutes（預設 300 分＝5 小時）→ 中斷
        return "running"
    return status or "pending"


def derive_recurring_health(item, now=None) -> str:
    now = now or datetime.now(config.TZ)
    data = item.data
    if data.get("status") != "active":
        return ""
    next_expected = _parse_dt(data.get("next_expected_at"))
    if not next_expected:
        return "ok"
    tolerance = int(data.get("tolerance_minutes") or config.DEFAULT_RECURRING_TOLERANCE_FLOOR)
    if now > next_expected + timedelta(minutes=tolerance):
        return "overdue"             # 週期性項目超過下次預期執行時間 → 逾期
    return "ok"

這不是即時監控：判定邏輯只在你執行 list 或 report 時才會回溯檢查一次，不會主動跳通知提醒你。沒有常跑 CLI 的習慣，這個系統就等於沒在監控——這也是為什麼 Bases 儀表板本身也需要你先跑一次 CLI，讓判定結果寫回 frontmatter，重新整理才看得到最新狀態。

CLI 快速上手

整套系統的日常操作幾乎都圍繞這幾個指令：

案例二：一個被中斷兩週多、沒人處理過的 Windows 排程

除了 Codex 委派紀錄，也去查了機器上真實存在的 Windows 工作排程器排程，發現一個叫 Codex-Resume-Claude-MicronYC-... 的一次性排程，是 2026-08-19 排定要續跑一個 Claude session， 結果因為 STATUS_CONTROL_C_EXIT（被中斷）而失敗——之後兩週多完全沒人再處理過。

把這筆排程登記進系統後（也就是前面 frontmatter schema 展示的 SCH-0048），audit 正確把它標成 stalled，rerun 指令也正確印出續跑建議：

真實執行輸出 
> python C:\VSCode_Proj\ClaudeCode\schedule-log\cli.py rerun SCH-0048

SCH-0048：Codex-Resume-Claude-MicronYC（Windows 排程續跑 session）
  status: stalled（started_at 2026-08-19T13:01:21+08:00，已超過 max_running_minutes=300）
  最後紀錄：interrupted (exit=3221225786 / STATUS_CONTROL_C_EXIT)
  resume_tool: claude / session_id: 6c17fc76-aebe-45b4-8194-6bcf0481bba2

建議的續跑指令（尚未執行，加上 --exec 才會真的觸發）：

  claude --resume "6c17fc76-aebe-45b4-8194-6bcf0481bba2"

> python C:\VSCode_Proj\ClaudeCode\schedule-log\cli.py rerun SCH-0048 --exec
（加上 --exec 後才會真的呼叫上面這行指令）

這裡的關鍵設計是：系統在建立項目時就把 session_id、working_dir、resume_tool 存進 frontmatter，重跑時才能正確重建出續跑指令。但刻意不會自動執行——一定要人加上 --exec 才會真的觸發，避免自動產生非預期的 API 用量。對 resume_tool: codex 的項目， CLI 更保守，完全不臆造續跑指令，只印出 original_prompt，建議走 codex:rescue 手動重新委派。

案例三：讓 Herdr 排程從「需要人補登」變成「全自動回報」

第三個案例是把系統跟一支真實存在的 Windows 排程 PowerShell 腳本 herdr-hourly-claude-greeting.ps1 串接起來——這支腳本每 20 分鐘執行一次，透過一個叫 herdr 的多 agent pane 管理工具，送出打卡問候給 Claude Code。做法是在腳本的 try/finally 加一段， 讓每次執行結束（不管成功、失敗、還是例外崩潰）都自動呼叫 CLI 的 run 指令回報執行狀態：

herdr-hourly-claude-greeting.ps1（節錄） 
# C:\Users\porte\scripts\herdr-hourly-claude-greeting.ps1（節錄）

$scheduleLogCli = "C:\VSCode_Proj\ClaudeCode\schedule-log\cli.py"
$itemId = "SCH-0047"

function Report-ScheduleLog {
    param([string]$Status, [string]$Note)
    try {
        python $scheduleLogCli run $itemId --status $Status --note $Note
    } catch {
        Write-Warning "schedule-log 回報失敗，但不中斷主流程：$_"
    }
}

try {
    # ...原本的 herdr 打卡問候邏輯（呼叫 herdr 送出訊息給 gyro / porter）...
    Report-ScheduleLog -Status "success" -Note "targets=gyro,porter 全部成功"
}
catch {
    Report-ScheduleLog -Status "failed" -Note "例外：$($_.Exception.Message)"
    exit 1   # 巢狀 try/finally 中，exit 陳述式依然會確實觸發 finally 區塊（已用隔離測試腳本驗證）
}
finally {
    # 不管上面走哪條路徑（成功 / 失敗 / exit），這裡永遠會執行
    Write-Host "本次執行已回報 schedule-log"
}

一個值得記住的 PowerShell 細節：PowerShell 的 exit 陳述式，即使在巢狀的 try/finally 裡，依然會確實觸發 finally 區塊——這不是憑印象假設，而是用一支隔離測試腳本實際驗證過的行為。這個細節正是「不管成功或失敗都能回報」的關鍵：只要回報邏輯放在 finally，就不用在每一條退出路徑上都重複寫一次。

接上這段之後，這個週期性排程從此變成全自動、不需要人工補登——這也是為什麼案例二（SCH-0048）跟案例三 （SCH-0047）恰好分別展示了一次性與週期性兩條路徑：前者示範漏跑後怎麼重跑，後者示範怎麼讓正常運作 的排程完全不需要人碰。

Bases 儀表板裡對應的「⚠️ 需要人工介入」view，就是靠這樣的公式欄位把三種異常統一呈現：

schedule-log.base（節錄） 
# schedule-log.base（節錄）
formulas:
  attention_since: if(status == "missed", scheduled_for, if(status == "stalled", started_at, next_expected_at))
  attention_reason: if(status == "missed", "🔴 逾期未跑（missed）", if(status == "stalled", "🟠 執行中斷超時（stalled）", "🟡 週期性逾期（overdue）"))

views:
  - type: table
    name: ⚠️ 需要人工介入
    filters:
      or:
        - status == "missed"
        - status == "stalled"
        - health == "overdue"
    sort:
      - property: formula.attention_since
        direction: ASC

三工具整合模式：純檔案格式作為資料交換層

本章開頭的三個孤島，最後是這樣被串起來的：

  • Claude Code：新增一個 skill，觸發詞是「排程」「看排程」等，而且會在查詢前先靜默同步一次 Codex 委派紀錄（自動跑 import-codex），使用者完全不用手動記錄委派任務。
  • Codex：在 Codex 的 AGENTS.md 規則檔加入指引，教它何時該呼叫這支 CLI（例如委派前登記一筆、完成後標記完成）。
  • Antigravity：這個工具原本完全沒有任何排程或待辦機制，比照既有的「workflow 模組」慣例（如既有的 workflow-printing-press.md）新增一個 workflow-schedule-log.md，讓它也能呼叫同一支 CLI。

值得記住的架構洞察：這證明了一件事——用純 Markdown + frontmatter 當資料交換格式，任何會下 shell 指令的 AI Agent 工具都能參與同一套系統，不需要專屬 SDK 或 API。三個工具彼此完全不需要互相認識，它們只需要知道同一支 CLI 的存在，以及同一個資料夾的路徑。這比為每個工具寫一個專屬整合插件，成本低得多，也更容易在未來加入第四個、第五個工具。

另外要老實說清楚這個系統的邊界：它是本機、單向鏡像系統——不會讀寫 Claude Code 原生 /schedule 的雲端排程資料，兩邊完全獨立；也不取代既有 PARA 系統裡的 projects/、 projects_PM/、brain/。它解決的是一個很具體的問題：「集中看到跨工具排程狀態， 並自動抓出漏跑與中斷」，而不是要變成一個全能的專案管理系統。

本章小結與下一步

這一章示範的不只是一個排程工具，而是一種思路：當你的工具鏈裡有好幾個各自為政的 AI Agent， 與其為每一個都學一套專屬的排程機制，不如退一步，用最樸素的 Markdown + YAML frontmatter 當共同語言， 讓 Obsidian（透過 Bases）扮演唯一的儀表板，讓一支輕量的 CLI 扮演唯一的資料存取層。

真實成效也證明了這個思路是划算的：一支 import-codex 指令就挖出 10 筆卡住超過 30 小時、 完全沒人發現的任務；一筆被中斷兩週多的 Windows 排程，被正確標記並給出可執行的續跑建議；一支既有的 PowerShell 排程腳本，只加了幾行 try/finally 就從「需要人工補登」變成「全自動回報」。

如果你想把這套方法套用到自己的工作流，不必照抄同一套 schema——核心可以遷移的只有三件事： 一，用檔案（而非資料庫或雲端服務）當資料交換層，任何工具都能參與； 二，把「這件事該發生的時間」跟「該完成的時間」都記下來，才能偵測「沒發生」而不只是記錄「發生了什麼」； 三，任何跟續跑、重試相關的動作，都預設只印出建議、不自動執行，把最終決定權留給人。
