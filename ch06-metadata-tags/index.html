Metadata 與標籤系統：讓筆記可以被找到

一則找不到的筆記，比沒有筆記更浪費時間

筆記消失的真正原因

你可能有過這樣的經歷：明明記得寫過某個主題，就是找不到。搜尋關鍵字找到了 20 則結果，但沒有一則是你要的。最後放棄，重新查資料，重新寫一遍。

問題通常不在於你沒有記筆記，而在於筆記缺乏可以被找到的結構。標題太模糊、沒有標籤、寫完就歸檔再也不看——這些筆記在 Vault 裡存在，卻無法被有效存取。

Obsidian 提供兩個互補的機制來解決這個問題：Properties（屬性）讓每則筆記帶有結構化的 Metadata，Tags（標籤）讓筆記可以跨資料夾歸類和篩選。兩者合用，才能讓知識庫真正可以被導航。

Properties：每則筆記的身分證

Obsidian 的 Properties 是放在筆記最頂部的 YAML 區塊，用 --- 包夾起來。它不是筆記的「內容」，而是筆記的「描述」——讓 Obsidian 和你自己快速了解這則筆記是什麼、什麼時候寫的、屬於哪些主題。 

---
title: 行為設計學讀書筆記
created: 2026/06/20
tags:
  - 行為心理學
  - 閱讀筆記
  - 習慣設計
description: BJ Fogg《設計你的小習慣》核心架構整理，包含動機/能力/提示三角模型與 Tiny Habits 方法論
重要性: ⭐⭐⭐⭐
---

Obsidian 1.4 之後，Properties 可以透過介面直接編輯，不需要手動寫 YAML。點擊筆記頂部的屬性區塊，即可用下拉選單和輸入框管理所有欄位。這個視覺化的 Properties 面板是 Obsidian 對新用戶最友善的改動之一。

Properties 的六種欄位類型

Obsidian 的 Properties 面板支援六種欄位類型，每種類型有不同的輸入介面和用途。選對類型，讓 Dataview 的查詢和排序事半功倍：

建議的欄位設計

一套實用的 Metadata 架構不需要複雜，以下欄位足以應付大多數情況：

  • title（Text）：筆記的完整標題（有時候檔案名稱是縮寫）
  • created（Date）：建立日期，格式統一 YYYY/MM/DD
  • tags（List）：主題標籤，3～8 個，kebab-case（見下節）
  • description（Text）：1～2 句話說明這則筆記的核心內容
  • 重要性（Number）：1～5 評分，配合 Dataview 排序用
  • published（Checkbox）：是否已完成/發布，用於篩選未完成項目

不要過度設計 Metadata：欄位太多反而讓你每次建立新筆記都有心理負擔。先從 3～4 個欄位開始，等到你發現「我常常需要按某個條件找筆記，但現在找不到」再新增對應欄位。Metadata 是為了解決真實痛點，不是為了讓結構看起來完整。

標籤系統：命名規範很重要

標籤讓你在不改動資料夾結構的情況下，為筆記加上多個維度的分類。一則筆記可以同時有 #閱讀筆記、#行為心理學、#2026 三個標籤——這是資料夾做不到的事。

命名規範：永遠使用連字號

Obsidian 的標籤不支援空白字元。如果你輸入 #Hermes Agent，系統只會把 #Hermes 識別為標籤，後面的 Agent 變成普通文字——這是初學者最常踩到的陷阱。 

# 標籤命名：三種可用格式

✅ 連字號（Kebab-case）— 強烈推薦
#行為心理學
#reading-notes
#product-management

✅ 底線（Snake_case）
#reading_notes

✅ 駝峰式（CamelCase）
#ReadingNotes

❌ 有空白 — 無效，只會識別到第一個詞
#reading notes   → 只有 #reading 生效
#Hermes Agent    → 只有 #Hermes 生效

巢狀標籤：用斜線建立層級

Obsidian 支援用 / 建立階層式標籤。#book/non-fiction 同時屬於 #book 大類和 #book/non-fiction 子類，讓你可以按不同粒度篩選。 

# 巢狀標籤範例

#book/non-fiction       → 屬於 #book 也屬於 #book/non-fiction
#project/active         → 進行中的專案
#project/completed      → 已完成的專案
#source/youtube         → 來源是 YouTube 影片
#source/article         → 來源是文章

→ 在標籤面板點開 #book，可以看到所有子標籤
→ 搜尋 #project 會同時找到 active 和 completed

推薦的四大頂層標籤系統

設計巢狀標籤時，頂層分類決定了你的整個查詢維度。以下是一套經過實踐驗證、通用性強的四大頂層結構： 

# 推薦的四大頂層標籤

#source/    → 來源類型
  /youtube  /article  /book  /podcast  /course

#topic/     → 主題領域
  /psychology  /productivity  /design  /tech

#status/    → 處理狀態
  /active  /done  /someday  /reference

#project/   → 所屬專案
  /work  /personal  /learning

# 使用方式：組合搭配
一則閱讀筆記可能同時有：
  #source/book
  #topic/psychology
  #status/done

避免標籤爆炸

標籤只有在「一個標籤下有多則筆記」才有意義。如果你有 200 個標籤，每個標籤底下只有 1～2 則筆記，標籤就失去了分類的作用。建議定期檢視標籤面板，把只出現一兩次的標籤合併或刪除。健康的標籤系統：30～50 個標籤，每個標籤下至少 3 則筆記。

不要用標籤記錄「這篇很重要」：#important、#must-read 這類標籤用一段時間後，幾乎每則筆記都會加上，完全失去篩選效果。改用 Number 類型的 重要性 欄位（1～5），用 Dataview 查詢才有意義。

在 Metadata 使用 [[內部連結]]

這是一個讓知識自動積累的技巧，許多 Obsidian 進階用戶都在用，但很少有人第一時間想到：在 Metadata 的欄位值裡放 [[內部連結]]，而不只是放文字。

作者筆記：追蹤思想脈絡

在 frontmatter 的 author 欄位，不要只填寫作者名字的純文字，而是連結到一則以作者命名的筆記： 

---
title: 《原子習慣》讀書筆記
author: "[[James Clear]]"
tags:
  - 閱讀筆記
  - 習慣設計
---

當你這樣做，James Clear 這則筆記的反向連結面板會自動顯示所有讀過他著作的筆記。久而久之，你不需要主動整理，這位作者的思想脈絡就會自然浮現——哪些書、哪些主題、哪些觀點之間有關聯，在 Graph View 裡一目了然。

主題 MOC：用連結取代標籤分類

傳統上，筆記主題用資料夾或標籤分類。但這兩種方式都有盲點：資料夾一個蘿蔔一個坑（一則筆記只能屬於一個資料夾），標籤看不出主題之間的關係。

更好的做法是在 Metadata 的 topics 欄位，用 [[]] 連結到主題筆記（Map of Content，簡稱 MOC）： 

---
title: 行為設計師讀書筆記
topics:
  - "[[行為心理學 MOC]]"
  - "[[產品設計 MOC]]"
  - "[[習慣養成 MOC]]"
---

這樣，一則筆記可以同時屬於多個主題，而且主題本身是「活的筆記」——你可以在 [[行為心理學 MOC]] 裡寫下這個主題和其他主題的關係，在 Graph View 看到叢集自然形成。

MOC 是什麼？ Map of Content（內容地圖）是一則專門用來連結其他筆記的索引筆記。它本身不需要有太多內容，主要的作用是成為某個主題的「交通樞紐」，讓相關筆記都能從它出發。MOC 在 ch07 的 LYT 系統中會有更詳細的介紹。

搭配 Dataview：讓 Metadata 產生動態視圖

如果你安裝了 Dataview 插件（第九章會詳細介紹），Metadata 的價值會再乘以十倍。你在 frontmatter 設定的每個欄位，都可以成為 Dataview 的查詢條件，自動生成表格、清單或任務看板。

關鍵在於：Metadata 的設計要從「我需要什麼樣的視圖」出發，而不是「我覺得應該記錄什麼」。

常見 Dataview 查詢範例

以下三個查詢展示了良好 Metadata 設計帶來的實際效益：

TABLE title, created, 重要性
FROM "閱讀筆記"
WHERE contains(tags, "reading/non-fiction")
SORT 重要性 DESC
TASK
FROM "專案"
WHERE status = "active" AND !completed
SORT due ASC

Dataview 也支援 Inline Field——在筆記正文中，用 欄位名:: 值 的格式直接加入可查詢的屬性，不需要全部集中在 frontmatter： 

---
title: 某篇會議紀錄
status:: active
due:: 2026/07/15
---

討論了產品路線圖，決定優先做 XX 功能。

# 待辦事項
- [ ] 寫提案文件 [due:: 2026/07/10]
- [ ] 安排下次會議

frontmatter vs. Inline Field：通用的結構化屬性（標題、日期、標籤）放 frontmatter；特定段落的臨時標記（這個待辦的 due date、這段引言的來源）用 Inline Field。兩者都可以被 Dataview 查詢。

完整的 Frontmatter 模板

把上面所有設計整合起來，以下是一個適合大多數筆記的完整 frontmatter 模板： 

---
title: 行為設計學讀書筆記
created: 2026/06/20
published: false
due: 2026/07/15
重要性: 4
tags:
  - reading/non-fiction
  - topic/psychology
description: BJ Fogg《設計你的小習慣》核心架構整理
author: "[[BJ Fogg]]"
topics:
  - "[[行為心理學 MOC]]"
  - "[[習慣設計 MOC]]"
---

不是每則筆記都需要填滿所有欄位。due 只在有截止日期時才填，published 只在追蹤完成狀態時才用。模板的作用是提醒你「有哪些選項」，而不是強制填滿每個格子。

三種分類法的比較

理解了 Properties、標籤和內部連結之後，自然會有個問題：我應該用哪一種？

  • 資料夾：適合存放「有明確歸屬」的筆記，例如特定專案的所有文件、特定年份的日記。優點是直覺；缺點是一則筆記只能放在一個地方。
  • 標籤：適合「橫跨多個資料夾的主題分類」，例如所有 #閱讀筆記，不管它們放在哪個資料夾。優點是靈活；缺點是標籤之間的關係不可見。
  • [[內部連結]]：適合「需要看出主題之間關係」的分類。連結本身就是一則可以有內容的筆記，可以在裡面寫脈絡、關係、演變，同時在 Graph View 視覺化。

實際上，這三種方法不是互斥的，而是搭配使用：資料夾作粗粒度的地理結構，標籤作快速篩選，內部連結做有語義的主題關聯。

從小開始：不要試圖一開始就設計出完美的分類體系。先用最少的欄位（title、created、tags），等到 Vault 累積到 50～100 則筆記，你才會知道自己真正需要哪些 Metadata 來找到想找的東西。

小結

Properties 讓筆記帶有結構化的身分資訊，標籤讓筆記可以被跨資料夾篩選，而在 Metadata 使用 [[內部連結]] 則讓知識的積累以一種你幾乎不需要刻意管理的方式自動發生。三者合用，才能讓 Vault 真正成為一個可以被導航、可以被探索的知識系統。

當你的 Metadata 設計夠完整，Dataview 插件可以在任何筆記裡生成動態彙整視圖——這是傳統資料夾歸檔完全做不到的事。下一章，我們把 Metadata 和每日筆記結合起來，讓 Obsidian 成為你每天思考的起點。
