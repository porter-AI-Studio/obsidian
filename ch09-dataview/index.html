Dataview：用查詢語法讓筆記自動彙整

你的 Vault 不只是筆記的倉庫，更是一個可以查詢的知識資料庫

當 Vault 越來越大，靠人工整理就輸了

你可能有過這樣的經歷：Vault 累積到一定數量後，想找「所有標記為重要的閱讀筆記」、「這個月修改過的所有專案筆記」、「所有連結到某個主題的筆記」——卻只能一則一則手動查找，或者在搜尋結果裡反覆過濾。

這個問題的根源不在搜尋，而在「展示方式」：全文搜尋找到的是結果清單，而你真正需要的是一張可以排序、可以篩選、可以隨筆記更新而自動刷新的動態表格。

Dataview 解決的正是這個問題。它讓你在任何一則筆記裡寫入一段查詢語法，Obsidian 就會在顯示時即時執行查詢、渲染出結果——而且每次開啟筆記，結果都是最新的。

Dataview 是什麼

Dataview 是一款社群插件，讓你用類 SQL 的查詢語言（DQL，Dataview Query Language）從整個 Vault 提取筆記資料。你可以把 Vault 想像成一個資料庫，每則筆記是一列資料，筆記的 Metadata（Properties）是各欄位——Dataview 就是讓你「SELECT 這些欄位 FROM 這個 Vault」的工具。

查詢結果支援三種呈現格式：

  • TABLE：表格，適合比較多則筆記的特定欄位
  • LIST：清單，適合快速列出符合條件的筆記標題
  • TASK：待辦事項，適合跨筆記彙整所有 - [ ] 任務

Dataview 與 ch06 的連結：Dataview 查詢的資料來源是每則筆記的 Metadata（Properties/YAML frontmatter）。這也是 ch06 強調「給筆記加上結構化屬性」的原因——沒有 Metadata，Dataview 就只能查詢檔案系統的內建欄位（建立時間、修改時間等），威力大打折扣。

維護狀態查證（2026-09 查證）：Dataview 原作者 blacksmithgu 自 2023 年起已放緩開發步調，官方 repository 累積數百個未處理 issue，主分支長期沒有新 commit。但截至查證當下，Dataview 並未被封存（archived）或標示為棄用，核心 DQL 查詢引擎自 2022 年起維持穩定、未受 Obsidian API 重大變更影響，本章示範的所有查詢語法仍可正常運作——可以視為「穩定但已凍結」的狀態安心使用，不必因此棄用它；只是若你需要新功能或積極的 bug 修復，社群回應速度會比幾年前慢很多。

在筆記中建立可查詢的欄位

在使用 Dataview 查詢之前，先確認你的筆記有可查詢的欄位。Dataview 支援兩種欄位來源：

方法一：YAML frontmatter（推薦）

在筆記頂部用 --- 包住的 YAML 區塊，所有欄位都可以被 Dataview 查詢。這也是 Obsidian 官方的 Properties 格式（ch06 介紹過）。 

---
title: 《原子習慣》讀書筆記
created: 2026-06-15
tags:
  - 閱讀筆記
  - 習慣設計
status: 🌱
重要性: ⭐⭐⭐⭐
author: "[[James Clear]]"
topics:
  - "[[習慣養成 MOC]]"
  - "[[行為心理學 MOC]]"
---

方法二：Inline field（彈性更高）

在 YAML 區塊外部，用 欄位名稱:: 值 的格式（雙冒號）定義行內欄位。這種格式更適合放 [[內部連結]] 的值，因為 YAML 裡放連結語法在技術上不夠規範。 

閱讀日期:: 2026-06-15
作者:: [[James Clear]]
重要性:: ⭐⭐⭐⭐⭐

何時用 Inline field？ 如果欄位值是 [[內部連結]]，或者你希望欄位直接顯示在筆記正文中（而不是折疊在 Properties 面板裡），用 Inline field 會更直觀。兩者可以混用——同一則筆記的 YAML frontmatter 和 Inline field 都可被 Dataview 查詢。

基本查詢語法逐行拆解

Dataview 查詢寫在一個特殊的 code block 裡，語言標記為 dataview：

```dataview
TABLE field1, field2
FROM #tag 或 "資料夾路徑" 或 [[筆記連結]]
WHERE 條件
SORT 欄位 asc/desc
```

第一行：選擇呈現格式與欄位

TABLE、LIST 或 TASK 決定輸出格式。TABLE 後面跟著你想顯示的欄位名稱，用逗號分隔。可以用 as "別名" 替欄位加上中文標題：

```dataview
TABLE file.mtime as "最後修改", 重要性, status as "狀態"
FROM #閱讀筆記
```

第二行：FROM — 決定資料來源

Dataview 支援三種來源語法：

  • FROM #tag：查詢帶有特定標籤的所有筆記
  • FROM "資料夾名稱"：查詢特定資料夾下的所有筆記（含子資料夾）
  • FROM [[筆記名稱]]：查詢所有連結到該筆記的筆記（反向連結）

第三行：WHERE — 篩選條件

常用的篩選條件：

```dataview
LIST
FROM #閱讀筆記

WHERE 重要性 >= "⭐⭐⭐"        ← 重要性大於等於 3 顆星
WHERE file.mtime >= date(today) - dur(7 days)  ← 最近 7 天修改
WHERE file.ctime >= date(today)                ← 今天建立
WHERE !contains(file.name, "MOC")              ← 排除包含 MOC 的檔名
WHERE status != null                           ← status 欄位有值
```

第四行：SORT — 排序

SORT 欄位 desc 倒序（最新到最舊），asc 正序（最舊到最新）。常見排序：SORT file.mtime desc（按修改時間）、SORT file.ctime desc（按建立時間）。

四種查詢類型深度比較

除了最常用的 TABLE、LIST、TASK，Dataview 還支援第四種類型 CALENDAR。以下是四種類型的使用要點：

  • TABLE：當你需要比較多則筆記的特定屬性，或製作可排序的報表時首選。可透過 as "別名" 讓欄位標題更易讀。
  • LIST：當你只需要看到符合條件的筆記標題清單，不需要額外欄位資訊時使用。輕量、簡潔，適合索引頁。
  • TASK：專為彙整 Markdown checkbox（- [ ] 和 - [x]）設計，查詢到的任務可在 Dataview 視圖中直接勾選完成，並同步回原始筆記。
  • CALENDAR：將筆記中的日期欄位映射到月曆視圖，特別適合 Daily Note 出勤圖或習慣打卡記錄的視覺化。
```dataview
CALENDAR file.ctime
FROM "Daily Notes"
```

CALENDAR 的前提：使用 CALENDAR 查詢時，Dataview 需要一個日期欄位作為映射基準。file.ctime 和 file.mtime 是內建欄位，可直接使用；如果想用自訂的 閱讀日期 或 created 欄位，只需確保其值為合法的日期格式（YYYY-MM-DD）即可。

DQL 語法完整結構

掌握這五個子句，就能覆蓋 90% 的 Dataview 使用情境：

  • 查詢類型（必填）：TABLE / LIST / TASK / CALENDAR，決定輸出格式
  • FROM（建議填）：指定資料來源；省略時查詢整個 Vault（可能很慢）
  • WHERE（選填）：篩選條件，支援 AND / OR / NOT 邏輯運算
  • SORT（選填）：排序規則，多欄位用逗號分隔
  • LIMIT（選填）：限制顯示筆數，避免結果過長

GROUP BY：進階分組查詢

除了以上五個子句，Dataview 還支援 GROUP BY，可以把結果依某個欄位值分組顯示——例如把所有筆記依 status 分組：

```dataview
TABLE rows.file.link as "筆記"
FROM #專案筆記
GROUP BY status as "狀態"
```

GROUP BY 的注意事項：使用 GROUP BY 後，TABLE 後面的欄位需要用 rows.欄位名稱 格式來引用，因為每一列現在代表一個分組，而非單一筆記。這是 Dataview 初學者常見的困惑點。

五個實戰案例

案例一：每日復盤 — 查看今天建立或修改的筆記

在 Daily Note 的模板裡加入這段查詢，每天打開日誌時就能自動看到當天所有有動靜的筆記，幫助你做當日回顧： 

```dataview
LIST
FROM ""
WHERE file.ctime >= date(today) OR file.mtime >= date(today)
SORT file.mtime desc
```

案例二：閱讀清單 — 彙整所有閱讀筆記並按重要性排序

建立一則「閱讀清單 MOC」，加入這段查詢，就有一張永遠是最新狀態的閱讀書單：

```dataview
TABLE file.link as "書目", author as "作者", status as "狀態", 重要性
FROM #閱讀筆記
SORT 重要性 desc, file.mtime desc
```

案例三：MOC 自動彙整 — 列出所有連結到某個主題的筆記

在任何一則 MOC（內容地圖）筆記裡加入這段查詢，就能自動顯示所有連結到這個主題的筆記，不需要手動維護清單。這是 Dataview 最讓人驚艷的用法之一： 

```dataview
TABLE file.mtime as "更新時間", status as "狀態", file.inlinks as "被引用次數"
FROM [[習慣養成 MOC]]
WHERE !contains(file.name, "MOC")
SORT status desc, file.mtime desc
```

案例四：跨筆記任務追蹤 — 彙整所有未完成待辦事項

如果你習慣在各筆記裡用 - [ ] 記錄待辦事項，Dataview 的 TASK 模式可以把它們全部提取到一個地方集中管理： 

```dataview
TASK
FROM "Projects"
WHERE !completed
SORT file.mtime desc
```

Dataview 查詢是即時的：以上所有查詢都是動態的——每次開啟包含查詢的筆記時，Dataview 都會重新掃描 Vault 並渲染最新結果。你不需要手動更新，新增或修改筆記後，相關查詢頁面會自動反映變化。

案例五：跨工具排程儀表板（實測案例，非教學範例）

前四個案例是常見的教學場景；這一個不是——它是 ch18 那套跨 AI 工具排程追蹤系統 （schedule-log/，`~45` 筆真實資料）的 Dataview 平行實作，用來驗證同一套 frontmatter schema 能不能同時服務 Bases 跟 Dataview 兩種檢視方式——答案是可以，資料格式完全沒有鎖定任何單一工具。

「⚠️ 需要人工介入」：抓出漏跑（missed）、中斷（stalled）、逾期（overdue）的項目：

```dataview
TABLE status, health, scheduled_for, started_at
FROM "schedule-log/items" OR "schedule-log/done"
WHERE status = "missed" OR status = "stalled" OR health = "overdue"
SORT scheduled_for ASC
```

用 GROUP BY type 做出「全部總覽」，一次性跟週期性項目分開顯示：

```dataview
TABLE WITHOUT ID rows.file.link as "項目", rows.status as "狀態"
FROM "schedule-log/items" OR "schedule-log/done"
GROUP BY type
```

只看週期性項目的執行狀態（schedule_kind 是 interval 還是 manual-trigger）：

```dataview
TABLE status, schedule_kind, last_run_at, next_expected_at
FROM "schedule-log/items"
WHERE type = "recurring"
SORT status ASC
```

跟 ch18 的 Bases 版本實測對照：這三個查詢都已經用 Dataview 的 API（tryQuery()）對 真實資料跑過，結果跟 Bases 版一致——同樣抓到 11 筆需要人工介入的項目。體感差異很明顯：Dataview 要手寫 DQL， GROUP BY 之後要改用 rows.欄位 語法才能攤開內容，比 Bases 點選介面設定分組來得繞； Dataview 也沒有 Bases 的 formulas 公式欄位，複雜邏輯得升級寫 DataviewJS（見下一節）才行。 兩種工具各有取捨，但**資料本身完全通用**，這是排程系統設計時刻意的決定。

Inline Dataview：在正文中嵌入即時數值

除了 code block 查詢，Dataview 還支援一種更輕量的用法——Inline Dataview，讓你在正文的任何位置嵌入即時計算值，語法是 `= 運算式`（反引號包住等號和運算式）。

常見用法：

  • `= this.status`：顯示當前筆記的 status 欄位值
  • `= this.file.mtime`：顯示當前筆記的最後修改時間
  • `= date(today)`：顯示今天日期
  • `= date(today) - this.created`：計算筆記建立後經過了幾天
# 《原子習慣》讀書筆記

**狀態**：`= this.status`
**建立時間**：`= this.file.ctime`
**距今已讀**：`= date(today) - this.file.ctime` 天

本書核心論點：...

Inline Dataview 的典型用途：在筆記 header 區域顯示「這則筆記的關鍵屬性」，例如狀態、最後更新時間、所屬專案等。這比手動維護這些資訊要可靠得多——值永遠是從 frontmatter 即時讀取的。

LIMIT 與 SORT 組合：打造最近 N 筆查詢

在儀表板或 MOC 筆記中，常常只需要「最近 10 筆」而非全部結果。SORT 搭配 LIMIT 是標準做法： 

```dataview
TABLE file.link as "筆記", 閱讀日期, 作者
FROM #閱讀筆記
WHERE 閱讀日期 >= date(today) - dur(30 days)
SORT 閱讀日期 desc
LIMIT 10
```

進階技巧：Dataview + Templater 搭配

案例三的 MOC 查詢有一個問題：你要在每一則 MOC 筆記裡手動填入對應筆記名稱。如果 MOC 數量多，這很繁瑣。

搭配 Templater（ch10 會詳細介紹），可以用 <% tp.file.title %> 變數自動帶入當前筆記名稱： 

```dataview
TABLE file.mtime as "更新時間", status as "狀態"
FROM [[<% tp.file.title %>]]
WHERE !contains(file.name, "MOC")
SORT file.mtime desc
```

將這段內容存為 Templater 模板，之後在任何新 MOC 筆記裡插入，查詢語法就會自動填入該筆記的名稱——一個模板，適用於所有 MOC。

Dataview vs DataviewJS：什麼時候需要升級？

Dataview 的 DQL（上面介紹的所有語法）適合 90% 的日常需求。但有些場景 DQL 無法滿足，這時可以升級使用 DataviewJS——用 JavaScript 撰寫查詢邏輯，語言標記為 dataviewjs。 

```dataviewjs
const pages = dv.pages('#閱讀筆記')
  .sort(p => p.file.mtime, 'desc')
  .slice(0, 5);

dv.table(['書名', '作者', '狀態'],
  pages.map(p => [p.file.link, p.author, p.status])
);
```

以下是選擇 DQL 還是 DataviewJS 的判斷依據：

  • 用 DQL 就夠的情境：篩選 + 排序 + 顯示欄位，絕大多數的閱讀清單、任務彙整、MOC 查詢。
  • 需要 DataviewJS 的情境：自訂輸出 HTML 結構、做複雜的資料轉換（例如統計標籤數量）、動態產生不規則的表格佈局、跨欄位的數學計算。

DataviewJS 的安全提醒：DataviewJS 本質上是在 Obsidian 環境裡執行 JavaScript，能力更強但也有風險——如果從外部複製來源不明的 DataviewJS 程式碼，請先理解它在做什麼再使用。DQL 則無此風險，因為它只有查詢能力，沒有執行任意程式碼的能力。

常見問題與注意事項

欄位名稱有大小寫之分

Dataview 的欄位名稱區分大小寫。如果 frontmatter 寫的是 Status，查詢裡就要用 Status，寫 status 會找不到資料。養成在整個 Vault 使用一致大小寫的習慣，能省去很多除錯時間。

Emoji 插入方式的坑

如果你用 Emoji 作為欄位值（例如 status: 🌱），不要透過某些插件工具列插入 Emoji——部分工具插入的是不同編碼格式，Dataview 無法正確讀取。直接從鍵盤輸入或複製貼上 Emoji 字元是最安全的做法。

查詢沒有結果時的系統化除錯步驟

遇到 Dataview 查詢沒有結果（或結果不符預期），按以下步驟逐步排查：

  1. 先用最簡單的查詢確認來源：只保留 LIST FROM #tag，確認標籤是否正確、是否有筆記帶這個標籤。
  2. 逐步加入篩選條件：確認來源正確後，再加入 WHERE，每次只加一個條件，確認哪一步開始結果為空。
  3. 檢查欄位名稱拼寫：打開一則應該出現在結果裡的筆記，對照 frontmatter 確認欄位名稱大小寫完全一致。
  4. 確認 Dataview 索引已更新：剛新增欄位後，有時需要等待幾秒讓 Dataview 重新索引，或用快捷鍵關閉再重新開啟該筆記。
```dataview
LIST
FROM #閱讀筆記
```

查詢沒有結果時怎麼辦？ 90% 的原因是：欄位名稱拼錯、標籤格式不對、或來源筆記沒有對應的 Metadata。遇到問題時，先用最簡單的查詢（只有 LIST FROM #tag）確認資料來源正確，再逐步加入 WHERE 和 SORT 條件縮小範圍。

小結

Dataview 把 Vault 從「靜態的筆記倉庫」變成「動態的知識資料庫」。只要你的筆記有一致的 Metadata 結構（這是 ch06 打好的地基），就能用幾行查詢語法換來永遠最新的自動彙整頁面——閱讀清單、每日復盤、主題 MOC、跨筆記任務追蹤，全都不需要手動維護。

本章重點回顧：四種查詢類型（TABLE/LIST/TASK/CALENDAR）各有最適合的情境；DQL 五個子句（查詢類型、FROM、WHERE、SORT、LIMIT）覆蓋日常 90% 需求；Inline Dataview 讓你在正文中嵌入即時數值；需要更複雜邏輯時再升級到 DataviewJS。

說到「減少重複勞動」，下一章我們要介紹 Templater 的進階用法——不只是插入日期的動態模板，而是讓 Obsidian 在新建筆記時自動套用格式、填入欄位，甚至根據規則把筆記自動移動到正確的資料夾。
