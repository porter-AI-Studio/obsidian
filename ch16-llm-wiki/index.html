第 16 章 · Part 5：AI 整合：打造 AI 驅動的知識庫

LLM Wiki 知識庫：讓知識自動進化

從 Karpathy 的靈感到你的個人知識庫自動化實作

傳統 RAG 的根本問題

你有沒有這個經驗：用 NotebookLM 或 ChatGPT 上傳一堆文件問問題， 得到了一個不錯的答案——然後對話視窗一關，什麼都沒剩下。

這就是傳統 RAG（Retrieval-Augmented Generation）最核心的缺陷。 每次提問，AI 都要從零開始在原始文件裡撈片段，拼湊出一次性的答案。 知識庫沒有結構，筆記之間沒有連結，過了對話視窗就什麼都不累積。

2026 年 4 月，前 Tesla AI 總監、OpenAI 共同創辦人 Andrej Karpathy 在 GitHub 發表了一份 Gist，叫做 LLM Wiki，收穫 5000 多顆星和近 2000 萬次曝光。 他在開頭就點破了問題所在：

「大多數人用 AI 處理文件的方式就是 RAG——每次都從零開始， 沒有累積，沒有沉澱。」

他的替代方案完全不同：不是每次查的時候才去原始文件撈， 而是讓 LLM 持續建構和維護一個 wiki——一組結構化、互相連結的 Markdown 檔案， 夾在你和原始資料之間。

他用一句話總結這個核心差異：「The wiki is a persistent, compounding artifact.」—— Wiki 是一個持久且不斷複利的產物。

Karpathy 的三層架構哲學

LLM Wiki 的精髓在於一個非常清晰的比喻： Obsidian 是 IDE，LLM 是工程師，Wiki 是程式碼。

Karpathy 在原文描述他的實際使用方式：「一邊開著 LLM Agent，一邊開著 Obsidian。 AI 根據對話內容編輯筆記，我即時瀏覽結果：追連結、看知識圖譜、讀更新後的頁面。」

這個分工讓知識管理的兩大障礙迎刃而解：

  • 人類負責：閱讀、思考、策展資料來源、問好問題
  • LLM 負責：整理、連結、維護、更新交叉引用——也就是所有 bookkeeping 苦工

Karpathy 的論點是：人類會放棄維護 wiki 不是因為懶， 是因為「維護成本的增長速度比價值還快」。 而 LLM 不會無聊，不會忘記更新交叉引用，一次能動 15 個檔案。

三層資料夾結構設計

要實作 LLM Wiki，第一步是在 Obsidian Vault 裡建立嚴格的資料夾邊界： 

ObsidianVault/
├── raw/                      # 原始素材區（唯讀證據庫）
│   ├── 2026-06-20-ai-agent.md
│   ├── 2026-06-20-llm-wiki.md
│   └── ...
│
├── wiki/                     # 知識百科區（AI 編譯輸出）
│   ├── Concepts/             # 概念條目（定義、核心觀點）
│   │   ├── RAG.md
│   │   ├── LLM-Wiki.md
│   │   └── ...
│   ├── Entities/             # 實體條目（人物、組織）
│   │   └── Andrej-Karpathy.md
│   ├── Sources/              # 來源摘要（文章摘要與關聯）
│   ├── index.md              # 整體目錄（AI 查詢導航起點）
│   └── log.md                # 操作日誌（追蹤 AI 做了什麼）
│
├── wiki/.drafts/             # 草稿審稿區（人工確認後才升格）
│   └── 待審核條目.md
│
└── CLAUDE.md                 # AI 行為規範說明書

三層的設計邏輯

  • raw/——原始素材區： 所有剪藏、RSS、手動貼入的文章都先放這裡。 這個資料夾是唯讀證據庫，原始脈絡和來源在這裡永遠不會被改動。
  • wiki/——知識百科區： AI 在這裡生成概念條目、實體條目、來源摘要。 這是不斷演化的知識網路，每加入新素材就會自動更新。
  • wiki/.drafts/——草稿審稿區： 第一次導入建議讓 AI 先輸出到草稿區，人工確認品質後再升格到正式 wiki。 這道防線能避免 Prompt Injection 或錯誤摘要污染知識庫。

原始素材不能丟，AI 結論要可審，人工修訂要優先——這三句話是這套架構最重要的設計原則。

三大核心操作：Ingest / Query / Lint

Karpathy 把 LLM Wiki 的日常操作歸納成三個動作。 在 Claude Code 的實作中，這三個動作對應三個 slash command，你可以直接在終端機呼叫：

Ingest（攝入）：/ingest-url 與 /process-inbox

Ingest 是把外部資訊「編譯」進知識庫的過程，有兩個入口：

  • /ingest-url <網址>—— 直接餵給 Claude Code 一個 URL，它自動抓取文章全文，提取出概念、實體、來源摘要， 一次最多觸及 5-15 個 wiki 頁面。這是最常用的入口，適合看到好文章當下立刻存入。
  • /process-inbox—— 掃描 raw/ 資料夾裡所有尚未處理的 Markdown 檔，批次分類並整合進 wiki。 適合用 Web Clipper 或 iOS 捷徑已經預先剪藏一批文章後，一次性消化。

每次 Ingest 的內部流程如下：

  1. 完整閱讀原文，提取核心概念（Concept）與提到的人物 / 組織（Entity）
  2. 搜尋 wiki/ 裡已有的相關條目，判斷是更新還是新建
  3. 更新或建立 wiki/Concepts/、wiki/Entities/、wiki/Sources/ 條目
  4. 補上 [[wikilink]] 交叉引用，更新 wiki/index.md 與 wiki/log.md

Ingest 不是剪貼，是「編譯」。 一篇 3000 字的文章 Ingest 後，wiki 裡可能多出 8 個更新的條目和 20 條新的交叉引用—— 這是傳統筆記工具做不到的知識密度提升。

Query（查詢）：從自己的知識庫問問題

Query 不需要特定 slash command——直接在 Claude Code 對話中提問即可。 關鍵是 Claude Code 會優先從你的 wiki/ 目錄中尋找答案， 而不是依賴它的訓練資料或即時網路搜尋。

這讓 Query 和普通 ChatGPT 的根本差異在於：

  • 答案來自你自己精選、標注過的素材，不是網路平均值
  • 引用的是你的 wiki/ 頁面（有出處可追溯），而非模糊的「我的訓練資料說」

Karpathy 特別強調一個關鍵洞察：

「好的回答應該被存回 wiki 變成新頁面，這樣你的探索也會像新資料一樣在知識庫裡產生複利。」

也就是說，你的提問本身就是一種 Ingest—— 每次有意義的 Q&A 都應該寫入 wiki/，未來的 Query 就能引用你自己問過的問題和答案。

Lint（健檢）：/lint-wiki

/lint-wiki 讓 Claude Code 掃描整個 vault，產出一份健診報告，找出：

  • 斷掉的 wikilink——指向不存在頁面的連結
  • 孤兒頁面——沒有任何其他頁面連入的條目（可能是遺忘的死角）
  • 內容矛盾——不同頁面對同一概念有衝突描述
  • 知識缺口——多次被提到但沒有獨立頁面的重要概念（這是下次 Ingest 的方向）
  • Frontmatter 不完整——缺少 title、tags、created 等必填欄位的筆記

Lint 是人類最容易偷懶跳過的步驟，但它是知識庫品質持續提升的關鍵機制。 建議每週跑一次，把報告中的「知識缺口」當作下週的閱讀清單—— 讓 Lint 的輸出驅動 Ingest 的輸入，形成自我強化的學習迴路。

Ingest 管道的內部機制

理解 Ingest 管道的每一步，有助於你在品質出問題時快速診斷。 以下是單篇文章從 raw/ 進入到 wiki/ 的完整流程：

最關鍵的是步驟 ③「Wiki 比對」：LLM 在寫入新內容之前，會先搜尋現有的相關條目， 決定是要更新既有頁面還是建立新頁面。 這個設計避免了「同一概念有多個分散條目」的知識碎片化問題。

來自 wiki 知識庫的洞察（[[摘要-VID-082-LLM-Wiki-深度解析]]）指出： 進階的 LLM Wiki 系統還會在此步驟加入「衝突偵測」—— 如果新文章對某個概念的描述與現有條目矛盾，會標記為 confidence: low 等待人工審查， 而不是直接覆蓋。

Wiki 條目的 Frontmatter 規範

好的 wiki 系統需要一致的 Frontmatter 格式。 這不只是整潔問題——一致的 confidence、sources、related 欄位， 讓 AI 在後續的 Query 和 Lint 時能做更精準的推理。 

---
title: "RAG 技術"
type: concept
tags:
  - 概念
  - AI
  - 知識管理
created: 2026-06-20
last_updated: 2026-06-20
confidence: high        # high / medium / low
sources:
  - "[[摘要-VID-019-RAG-工作機制詳解]]"
  - "[[摘要-VID-082-LLM-Wiki-深度解析]]"
related:
  - "[[LLM Wiki]]"
  - "[[向量資料庫]]"
  - "[[語義搜索]]"
---

## 定義
RAG（Retrieval-Augmented Generation）是一種結合檢索與生成模型的技術，
先搜尋相關知識文件，再將結果作為上下文輸入語言模型，以提升回應準確性。

## 關鍵資訊
- 結合向量檢索系統與大型語言模型
- 可即時引入最新資料，降低重訓成本
- 主要應用於法律、醫療、客服等專業領域
- 支持增量更新資料庫，而不必重新訓練整體模型
- 增強回覆可追溯性與解釋性

## 與 LLM Wiki 的差異
| 面向 | RAG | LLM Wiki |
|------|-----|----------|
| 處理時機 | 查詢時即時撈取 | 寫入時預先編譯 |
| 知識積累 | 每次從零開始 | 持續複利累積 |

## 關聯連接
- [[Andrej Karpathy]]
- [[LLM Wiki]]
- [[向量資料庫]]

confidence 欄位的設計哲學： 設定 high 的條目表示有多個來源佐證、且未見矛盾； low 表示只有單一來源或曾出現過衝突描述，查詢時應謹慎引用。 這讓你的 wiki 從「筆記堆」升級成「帶可信度權重的知識圖譜」。

用 Python 自動化 Ingest 流程

如果你想要不依賴任何第三方工具，直接用 Anthropic API 自己打造 ingest 腳本， 以下是一個完整的最小可用範本： 

#!/usr/bin/env python3
"""
wiki_ingest.py — 將 raw/ 目錄的 Markdown 文件編譯進 wiki/
用法：python wiki_ingest.py --vault /path/to/vault --file raw/2026-06-20-ai-agent.md
"""
import sys, io, argparse, json
from pathlib import Path
from datetime import datetime

if sys.platform == 'win32':
    sys.stdout = io.TextIOWrapper(sys.stdout.buffer, encoding='utf-8', errors='replace')

import anthropic  # pip install anthropic

SYSTEM_PROMPT = """你是 Obsidian Vault 的 AI 知識管家。
根據輸入的原始文章，輸出 JSON 格式的 wiki 更新計畫：
{
  "concepts": [{"title": "...", "definition": "...", "key_facts": [...]}],
  "entities": [{"name": "...", "type": "person|org|tool", "description": "..."}],
  "source_summary": "...",
  "wikilinks": ["[[概念A]]", "[[概念B]]"]
}
保持 NEVER 刪除現有內容的原則。"""

def ingest_file(vault_path: Path, file_path: Path) -> dict:
    client = anthropic.Anthropic()
    article = file_path.read_text(encoding='utf-8')

    message = client.messages.create(
        model="claude-sonnet-4-5",
        max_tokens=4096,
        system=SYSTEM_PROMPT,
        messages=[{"role": "user", "content": f"請分析此文章並回傳 JSON：\n\n{article}"}]
    )

    raw = message.content[0].text
    plan = json.loads(raw[raw.find('{'):raw.rfind('}')+1])

    # 寫入 wiki/Concepts/
    for concept in plan.get("concepts", []):
        slug = concept["title"].replace(" ", "-")
        out = vault_path / "wiki" / "Concepts" / f"{slug}.md"
        out.parent.mkdir(parents=True, exist_ok=True)
        if not out.exists():
            out.write_text(build_concept_md(concept), encoding='utf-8')
            print(f"  + 建立概念：{out.name}")

    # 寫入 wiki/Sources/
    date_str = datetime.now().strftime("%Y-%m-%d")
    source_slug = file_path.stem
    source_out = vault_path / "wiki" / "Sources" / f"摘要-{source_slug}.md"
    source_out.write_text(
        f"---\ntitle: 摘要-{source_slug}\ntype: source\n"
        f"created: {date_str}\nsources: [{str(file_path)}]\n---\n\n"
        f"## 核心摘要\n{plan['source_summary']}\n\n"
        f"## 關聯連接\n" + "\n".join(f"- {w}" for w in plan["wikilinks"]),
        encoding='utf-8'
    )
    print(f"  + 寫入來源摘要：{source_out.name}")
    return plan

def build_concept_md(concept: dict) -> str:
    date_str = datetime.now().strftime("%Y-%m-%d")
    facts = "\n".join(f"- {f}" for f in concept.get("key_facts", []))
    return (
        f"---\ntitle: {concept['title']}\ntype: concept\n"
        f"tags: [概念]\nlast_updated: {date_str}\n---\n\n"
        f"## 定義\n{concept['definition']}\n\n"
        f"## 關鍵資訊\n{facts}\n\n## 關聯連接\n"
    )

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--vault", required=True, help="Vault 根目錄路徑")
    parser.add_argument("--file", required=True, help="要 ingest 的 raw/ 檔案")
    args = parser.parse_args()
    vault = Path(args.vault)
    target = vault / args.file
    print(f"Ingesting: {target.name}")
    result = ingest_file(vault, target)
    print(f"完成！處理了 {len(result.get('concepts',[]))} 個概念")

這個腳本的設計遵循 LLM Wiki 的核心原則： 讓 LLM 做分析和結構化的苦工，人類只做策展（選擇哪些文章值得 ingest）。 調整 SYSTEM_PROMPT 中的規則，即可客製化你的知識庫風格。

實作：安裝 obsidian-llm-wiki

開源社群把 Karpathy 的概念做成了可直接安裝的工具——obsidian-llm-wiki， 預設支援 Ollama 作為本地 LLM Provider，讓你的知識整理完全在本機運行，零隱私外洩。

雙模型架構推薦

在開始安裝前，先規劃你的模型配置：

  • Fast Model：負責快速分類、路由、初步實體辨識。建議從 gemma4:e4b 入手。
  • Heavy Model：負責深度萃取、知識融合、條目改寫。建議 14B 以上；顯卡 12GB+ 可嘗試量化版 14B 模型。

實務建議：不要一開始就追求最強模型，先確認工作流能跑通， 產出的 Wiki 條目結構合理、來源可追溯，再來升級模型。 

# 步驟一：確保 Python 3.11+ 已安裝
python --version

# 步驟二：建立獨立虛擬環境（避免污染全域）
python -m venv olw-env
source olw-env/bin/activate   # macOS / Linux
# olw-env\Scripts\activate   # Windows

# 步驟三：安裝 obsidian-llm-wiki
pip install -U pip
pip install obsidian-llm-wiki

# 步驟四：進入你的 Obsidian Vault 根目錄
cd /path/to/ObsidianVault

# 步驟五：初始化設定（互動式精靈）
olw setup
# Provider 選擇 Ollama
# API URL：http://127.0.0.1:11434（本機）
# 或 http://192.168.x.x:11434（遠端 NAS/AI PC）
# 綁定 Fast Model 與 Heavy Model

# 步驟六：健康檢查
olw doctor

# 步驟七：第一次執行（先用少量文章測試）
olw run

# 確認品質後，切換到監控模式（自動處理新進 raw/）
olw watch

第一次不要直接開全自動批准。讓 AI 先產生草稿（進入 wiki/.drafts/），人工確認品質後再改用 olw watch 進入監控模式。這樣可以避免概念混淆或來源誤讀污染正式知識庫。

資料收集的四種方案

raw/ 資料夾是整套系統的入口，你需要決定「怎麼把外界資訊送進來」：

  • 方案 A：Obsidian Web Clipper（推薦新手）—— 在瀏覽器看到好文章，一鍵剪藏為 Markdown 存入 raw/。 最少外部依賴，最容易除錯。
  • 方案 B：iOS 捷徑分享流—— 手機上分享 URL 給捷徑，使用 Jina Reader（r.jina.ai/[網址]）轉換成乾淨 Markdown， 儲存到 iCloud 同步的 vault。適合通勤重度使用者。
  • 方案 C：Wallabag—— 自架稍後閱讀服務，資料完全自主，適合重視長期可控性的使用者。
  • 方案 D：RSS + n8n 全自動訂閱—— 固定追蹤媒體或 GitHub releases，n8n 自動抓取全文寫入 raw/。 什麼都不用做，追蹤的媒體一發文知識庫就自動更新。

建議從方案 A 開始，等整套流程跑穩後再逐步導入自動化。複雜的收集系統失敗時更難除錯，先確保 AI 編譯的品質，再來擴充資料入口。

CLAUDE.md：AI 的行為規範說明書

不管你用哪個工具，讓 Claude Code 直接操作 vault 時， 根目錄的 CLAUDE.md 是整個工作流的基石。 它告訴 AI 這個 vault 的結構規則、什麼可以動、什麼絕對不能碰。 

# Vault 規範（CLAUDE.md 範本）

## 身份與範圍
你是這個 Obsidian Vault 的 AI 知識管家。
只操作本 vault 內的 .md 檔案。

## 資料夾結構
- raw/        原始素材，只讀不改
- wiki/       AI 整理後的知識條目
- daily/      每日筆記（YYYY-MM-DD.md）
- projects/   進行中的專案
- resources/  參考資料

## 行為規範
- NEVER 刪除任何檔案
- NEVER 修改 raw/ 目錄下的檔案
- NEVER 改動已存在的 frontmatter tags（只能新增）
- 所有 wikilink 使用 [[雙括號]] 格式
- frontmatter 必填：title、tags、created、source

## Ingest 規則
新文章放入 raw/ 後，ingest 時需：
1. 提取核心概念，更新或建立 wiki/Concepts/ 條目
2. 提取提到的人物/組織，更新 wiki/Entities/ 條目
3. 在 wiki/Sources/ 建立來源摘要頁
4. 更新 wiki/index.md 和 wiki/log.md

CLAUDE.md 的關鍵設計原則

內容建議控制在 100 行以內——太長會浪費 token，也容易讓 AI 混淆。 最重要的是寫清楚 NEVER 清單：明確禁止刪除檔案、修改 raw/ 目錄、 改動已有 tags 等不可逆操作。AI 工具最危險的不是它不會做什麼， 而是它太積極了。

Wiki Query 工作流：讓提問也變成 Ingest

根據 Karpathy 的原始設計，LLM Wiki 最有趣的特性是「提問即積累」—— 你向 wiki 問一個問題，AI 整合了 5 個相關條目回答你， 然後這個答案本身會被寫回 wiki 成為新條目，供下一次 Query 引用。

以下是在 Claude Code 中設置 wiki query 的 slash command 範本： 

# 在 Claude Code 對話中直接提問 wiki
# 以下是 .claude/commands/wiki-query.md 的範本內容

---
description: 從個人 wiki 知識庫回答問題，答案自動存回 wiki
---

請依照以下步驟回答：

1. 先搜尋 wiki/Concepts/ 和 wiki/Entities/ 找相關條目
2. 搜尋 wiki/Sources/ 找原始來源佐證
3. 整合這些知識回答問題：$ARGUMENTS
4. 如果這個問題的答案值得保存（關鍵洞察、決策依據），
   在 wiki/Concepts/ 建立新頁面或更新既有頁面
5. 在 wiki/log.md 追加一筆 [QUERY] 紀錄

回答格式：
- 直接回答問題
- 引用的 wiki 頁面：[[頁面名稱]]
- 是否已寫回 wiki：是/否（說明原因）

什麼樣的答案值得寫回 wiki？ 判斷標準是：這個答案三個月後我還會想找嗎？ 如果是的話，就讓 AI 把它整理成一個 Concept 條目存入 wiki/Concepts/。 決策依據、技術比較、個人洞察——都是值得沉澱的知識，而不只是一次性的問答。

RAG vs LLM Wiki：架構根本差異視覺化

傳統 RAG 和 LLM Wiki 的根本差異不只是技術選擇，而是兩種完全不同的知識觀： 一個把知識當作「可以即時撈取的原料」，另一個把知識當作「需要持續精煉的資產」。

Wiki 知識圖譜：條目如何形成互連網路

LLM Wiki 最迷人的特性之一，是在 Obsidian 的圖譜視圖（Graph View）中清晰可見的知識網路。 每個 wiki 條目都是一個節點，每條 [[wikilink]] 都是一條邊。 當你 ingest 的文章越多，這個網路就越密集、越有意義。

這個圖譜不只是視覺化的展示——它直接反映了你的知識結構。 高連接度的節點是你的核心概念，孤立的節點（沒有邊連入）是 Lint 應該處理的孤兒頁面。 圖譜的密度越高，代表你的知識庫整合度越好，查詢時 AI 能找到的上下文也越豐富。

從知識庫的角度看 Obsidian 圖譜： 每次 ingest 後打開 Graph View，你可以直觀地看到哪些概念因為這篇文章變得更被連結。 如果一篇文章 ingest 後圖譜幾乎沒有變化，表示這篇文章和你的既有知識庫重疊度很高； 如果圖譜出現很多新節點，表示這篇文章帶來了全新的知識領域。

三個實戰工作流

每日筆記自動生成

在 .claude/commands/today.md 放入指令： 「檢查今天的 daily note 是否存在，沒有就用 templates/daily.md 建立， 然後從昨天搬入未完成的待辦事項」。 之後每天打 /today，10 秒內完成。

批次加反向連結

讓 Claude Code 掃描最近一個月的 daily notes，找出所有提到的人名、專案名、書名， 自動補上 [[wikilink]]。沒有對應筆記的就自動建立 entity page。 一個下午的手動工作，幾分鐘搞定，而且從此每次 ingest 都會自動維護這些連結。

每週回顧自動生成

設定 /weekly-review 指令，Claude Code 統計本週完成和未完成的 tasks、 辨識重複出現的主題、找出停滯的專案，產出一份結構化回顧筆記。 這份回顧本身也是 Obsidian 筆記，未來的 AI 查詢可以引用——這就是 LLM Wiki 的複利效應。

與傳統 RAG 的根本差異

面向 傳統 RAG LLM Wiki
處理時機 查詢時即時撈取 寫入時預先編譯
儲存格式 向量資料庫 Markdown 純文字
知識積累 每次從零開始 持續複利累積
建置複雜度 需要向量 DB 基礎設施 只需 Obsidian + Ollama
適用規模 數萬篇以上 個人規模約 100 篇最佳
可讀性 向量不可人工閱讀 Markdown 隨時可瀏覽
查詢答案去向 一次性，對話結束即消失 可寫回 wiki 持久保存

LLM Wiki 的規模限制：這套方法適合個人知識庫，約 100 篇文章的規模效果最好。知識庫越大，每次查詢讀取的 Token 越多，成本線性增長。如果你的資料規模達到數萬篇，傳統 RAG 的向量搜尋方案反而更合適。

本章小結

Karpathy 的 LLM Wiki 哲學用一個洞察解開了知識管理的根本矛盾： 人類放棄維護 wiki 不是因為懶，是因為 bookkeeping 的成本太高。 LLM 不會無聊，不會遺忘，才是真正適合做 bookkeeping 的存在。

這套架構讓 Obsidian vault 從「筆記倉庫」進化成「持續自我演化的個人維基百科」： Raw 是原料，Wiki 是精煉成果，Ingest / Query / Lint 三個動作讓知識庫越用越豐富。 每加入一篇新文章，整個知識網路都會因此變得更完整。 每一次有意義的提問，都是對知識庫的一次 Ingest。

這一章的知識，配合前兩章（ch14 Claude Code + Obsidian、ch15 Obsidian CLI 與 AI Skills）， 構成了完整的 AI 知識管理三層架構。下一章我們回到基礎設施層： 多終端同步——讓你在手機、電腦、平板上都能看到同一個 vault，不遺漏任何靈感。
