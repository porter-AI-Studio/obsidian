第 13 章 · Part 4：Web Clipper 與資訊收集

進階剪藏：自訂模板與 AI 自動摘要

讓 AI 在剪藏的瞬間就讀懂你的資料，而不是等你以後有空再整理

從「存進去」到「讀懂再存」

上一章我們設定好了 Web Clipper 的基礎流程：點一下，進 Vault。 但「進了 Vault 放著」和「進了 Vault 就有摘要、有標籤、有脈絡」， 是完全不同的知識管理體驗。

Web Clipper 的進階功能核心是 AI 解釋器（Interpreter）—— 它讓你的模板不只能抓取網頁的靜態資訊，還能在剪藏時即時呼叫大語言模型， 用自然語言指令對內容做摘要、翻譯、重新結構化。 本章從解釋器的設定開始，一路到多場景模板設計和中文平台的進階支援。

AI 解釋器：讓 LLM 參與剪藏過程

普通變數 vs AI 解釋器變數

Web Clipper 的變數分兩類，理解這個差異是設計好模板的關鍵： 

// 普通變數：插件從網頁 HTML 直接抓取
{{title}}     → 讀取 <title> 標籤
{{author}}    → 讀取 meta[name="author"]

// AI 解釋器變數：插件把頁面內容送給 LLM，由 AI 計算填入
{{ai:請用 3 點條列這篇文章的核心論點，每點不超過 20 字}}
{{ai:如果這篇文章是一本書的某章，它的章節標題會是什麼？}}

普通變數（{{title}}、{{url}}） 是從網頁 HTML 直接讀取固定欄位，速度快、不需要 API Key。 AI 解釋器變數（{{ai:...}}）則是把整個頁面內容送給你指定的 LLM， 讓 AI「讀懂」之後填入這個位置——相當於每次剪藏都有一個 AI 助理幫你預處理。

開啟並設定解釋器

  1. 點擊瀏覽器工具列的 Web Clipper 圖示
  2. 點右上角齒輪進入設定
  3. 選擇「Interpreter」頁籤（預設關閉，需手動啟用）
  4. 點「Add provider」新增 AI 供應商，填入 API Key
  5. 選擇模型

選哪個模型？ 強烈建議選小型、速度快的模型，例如 Gemini 1.5 Flash 或 Claude Haiku。每次剪藏都會呼叫 API，如果用 GPT-4o 等大模型，等待時間會長達數十秒，嚴重影響使用意願。小模型每篇成本不到 0.01 美元，速度卻快 3-5 倍。如果你有架設 Ollama 本地模型（第 15 章），也可以完全免費且零延遲。

模板觸發器：對的網站，自動套對的模板

你可能有多個模板：技術文章模板、YouTube 影片模板、學術論文模板…… 每次剪藏都要手動切換，累積下來是不小的摩擦力。 模板觸發器（Template Triggers）允許你為每個模板設定 URL 規則， 打開符合規則的網頁時，Web Clipper 會自動預選對應的模板。 

// 模板觸發器範例（在模板設定的頂部配置）

// 視頻模板（YouTube + B站）
URL 規則 1：youtube.com/watch
URL 規則 2：bilibili.com/video

// 學術論文模板
URL 規則 1：arxiv.org/abs
URL 規則 2：pubmed.ncbi.nlm.nih.gov

// 公眾號模板
URL 規則：mp.weixin.qq.com

觸發器設定位置：在模板編輯頁面的最頂部，有一個「Template triggers」欄位，可以新增多條 URL 規則（支援部分字串比對）。同一個模板可以配多條規則；如果多個模板的觸發器都符合，以列表中排序最前面的模板優先。

高亮文本同步：邊讀邊標記，自動進 Vault

Web Clipper 有一個常被忽略的功能：在網頁上直接用滑鼠選取文字， 點擊 Web Clipper 的高亮按鈕，這段文字就會被標記。 當你最後執行「Add to Obsidian」時，所有高亮的段落會自動彙整到模板的 {{highlights}} 變數中。

這個工作流的好處是：

  • 讀文章時一邊劃重點，不需要切換視窗
  • 剪藏後笔記裡已經有「你認為重要的段落」，不必再回頭整理
  • 搭配 AI 變數，可以讓 AI 只針對你高亮的部分生成摘要，而不是整篇文章

進階用法：在模板中同時放 {{highlights}} 和 {{content}}，並用 AI 變數 {{ai:根據以下高亮段落，推斷這篇文章對我最有用的應用場景}}，讓 AI 只分析你標記的部分，節省 token 又更精準。

組合技：沉浸式翻譯 + Web Clipper

如果你習慣使用「沉浸式翻譯」瀏覽器擴充功能閱讀英文文章， 有一個省時技巧：不需要在 Web Clipper 設定翻譯解釋器， 只需在沉浸式翻譯開啟的頁面直接使用 Web Clipper—— 它會同時抓取原文和翻譯後的中文，讓筆記裡同時保留雙語版本。

這個方式比在 Web Clipper 內設定翻譯 AI 變數更快，因為：

  • 沉浸式翻譯已經在頁面渲染翻譯結果，Web Clipper 直接抓取 HTML，不需額外 API 呼叫
  • 翻譯品質可由沉浸式翻譯的設定控制（支援 DeepL、Claude 等引擎）
  • 剪藏速度更快，沒有等待 AI 回應的延遲

模板設計原則：AI 變數的 prompt 越具體，輸出品質越高。避免用「總結這篇文章」這種泛化指令，改用「用繁體中文，條列三個技術觀點，每點不超過 20 字」——語言、格式、數量、長度都明確，AI 的輸出才會一致。

中文增強版：Obsidian Clipper CN

官方 Web Clipper 對中文平台的支援有限，社群開發者 Next蔡蔡 維護的 obsidian-clipper-cn（GitHub: nextcaicai/obsidian-clipper-cn） 在官方版本基礎上增加了兩個重要的中文平台支援：

B 站影片支援

  • 提取影片簡介、章節時間軸、完整字幕
  • 在 Obsidian 的 Reader Mode 中嵌入 B 站播放器，可按時間軸自訂跳轉
  • 搭配 AI 解釋器，可自動生成影片摘要（與 YouTube 體驗一致）

飛書文件支援

飛書文件需要透過 API 才能讀取結構化內容，設定流程如下：

  1. 前往飛書開放平台（open.feishu.cn），建立一個「自建應用」
  2. 為應用開通 Wiki 相關權限（wiki:wiki:readonly 等）
  3. 建立版本並發布（未發布的應用無法使用 API）
  4. 從「憑證與基礎資訊」頁面取得 App ID 和 App Secret
  5. 在 Obsidian Clipper CN 設定的底部「飛書模塊」填入這兩個值

隱私說明：App ID 和 App Secret 僅儲存在你的本機瀏覽器中，不會上傳到任何伺服器。目前飛書版本的限制是無法擷取文件中的圖片，其他文字內容可完整保存。

為什麼不合併進官方版本？ 作者曾嘗試向官方提交 PR，但官方的定位是 Web Clipper 只處理其自有工具處理後的內容，因此中文平台的支援被拒絕合併。這就是為什麼需要使用獨立維護的 obsidian-clipper-cn。

剪藏工作流的完整建議

把本章與上一章的功能串聯起來，建議的最佳實踐工作流如下：

  1. 設定 2-4 個情境模板（技術文章、影片、論文、社群貼文），每個模板配觸發器 URL
  2. 每個模板內放 1-2 個 AI 變數，用小型模型生成摘要，不追求面面俱到
  3. 閱讀時用高亮功能標記重點，剪藏後的筆記已包含你認為值得記錄的段落
  4. 英文內容配合沉浸式翻譯，同時保留原文與中文翻譯
  5. 中文平台（B 站、飛書）用 obsidian-clipper-cn
  6. 定期用 Obsidian Base（第 12 章提到）審視剪藏庫，把「已讀未整理」的筆記標記狀態

剪藏不是終點：Web Clipper 解決的是「收集」這個環節的摩擦，但知識管理的價值在於「回顧與連結」。建議每週花 15-20 分鐘瀏覽本週的剪藏，加入雙向連結，讓這些資訊真正融入你的 Vault 知識網絡（見第 4 章）。

Handlebars 進階模板語法

Web Clipper 的模板引擎底層使用 Handlebars 語法， 除了基本的 {{變數名}} 插值，還支援條件判斷、迭代陣列與巢狀邏輯， 讓模板根據剪藏的網頁類型動態調整輸出結構。 

{{! 條件渲染：只在有作者時顯示 }}
{{#if author}}
author: "{{author}}"
{{/if}}

{{! 陣列迭代：把 tags 陣列展開成 YAML 清單 }}
tags:
{{#each tags}}
  - {{this}}
{{/each}}

{{! 巢狀條件：學術論文才加 doi 欄位 }}
{{#if (includes url "arxiv.org")}}
doi: "{{doi}}"
{{/if}}

{{! 選取文字優先，沒有就用全文 }}
{{#if highlights}}
{{highlights}}
{{else}}
{{content}}
{{/if}}

幾個實用技巧：

  • {{#if author}}：只在頁面有 meta[name="author"] 時才寫入 author 欄位，避免空值出現在 frontmatter
  • {{#each tags}}：把 Clipper 抓到的多個標籤自動展開為 YAML 清單格式
  • {{#if highlights}}...{{else}}{{content}}：有選取文字時插入高亮段落，否則 fallback 到全文——讓「快速剪藏」和「精選剪藏」使用同一個模板

includes helper：Clipper 內建了 {{#if (includes url "arxiv.org")}} 這類 helper，可以對 URL 做字串比對。這讓同一個模板在剪藏學術論文時自動加入 DOI 欄位，剪藏其他頁面時省略，比分成兩個模板更易維護。

Schema Interpreter：用 AI 自動萃取結構化 Properties

一般的 AI 解釋器用法是讓 AI 生成「摘要文字」填入筆記內文。 Schema Interpreter 則是把 AI 變數放進 frontmatter， 讓 AI 直接推斷並填入結構化屬性——分類、難度、閱讀時間、技術清單—— 這些屬性日後可以被 Dataview 直接查詢，真正做到「剪藏即結構化」。 

---
title: "{{title}}"
source: "{{url}}"
author: "{{author}}"
created: {{date:YYYY-MM-DD}}

{{! Schema Interpreter：AI 自動萃取結構化屬性 }}
category: "{{ai:判斷這篇文章最適合的分類，從以下選項選一個：技術教學/產品評測/觀點分析/新聞/學術}}"
difficulty: "{{ai:這篇技術文章的難度是？回答 beginner / intermediate / advanced 其中一個}}"
estimated_read: "{{ai:這篇文章約需幾分鐘閱讀？只回答數字}}"
technology:
{{ai:條列這篇文章提到的技術工具名稱（每行一個），最多 5 個，格式：  - 工具名稱}}
---

{{content}}

Schema Interpreter 的成本意識：frontmatter 裡每個 {{ai:...}} 都是一次獨立的 LLM 呼叫。建議把相關的屬性合併成一個 prompt，例如「請用 JSON 格式回傳以下欄位：category、difficulty、estimated_read、technology（陣列）」，再用 Handlebars 解構輸出——把 4 次 API 呼叫壓縮成 1 次，速度更快、成本更低。

自訂 Properties 映射策略

不同網站的元數據品質差異極大：有些網站 meta[name="author"] 是空的， 有些網站把作者名稱放在特定的 CSS class 裡而非 meta 標籤。 這時可以用 AI 做 fallback 映射：

  • 作者欄位：{{#if author}}{{author}}{{else}}{{ai:從文章內容推斷作者名稱，只回傳名字}}{{/if}}
  • 出版日期：當 {{date}} 讀取到的是今天（表示網頁沒有發布日期 meta）時，改用 AI 在文章中搜尋日期線索
  • 主題分類：讓 AI 根據你自定義的分類體系（PARA、Zettelkasten 等）把文章放入對應類別

Clipper + Dataview：剪藏後自動建立動態閱讀清單

Schema Interpreter 的最大回報，體現在和 Dataview 的整合。 當每篇剪藏筆記的 frontmatter 都有一致的結構化屬性後， 你只需要在一個「閱讀清單 MOC」筆記裡放一段 Dataview 查詢語句， 就能自動看到所有待讀文章——不需要手動維護清單。

待讀清單 Dataview 查詢

```dataview
TABLE source, category, estimated_read, created
FROM "Clippings"
WHERE contains(tags, "to-read")
SORT created DESC
LIMIT 20
```

進階：未讀過濾 + 分類排序

```dataview
TABLE
  source AS "來源",
  category AS "分類",
  estimated_read AS "預估(分鐘)",
  created AS "收藏日期"
FROM "Clippings"
WHERE !contains(file.tags, "read") AND contains(file.tags, "to-read")
SORT created ASC
```

建立閱讀進度追蹤：在每個剪藏筆記的 frontmatter 加入 status: to-read 欄位（Web Clipper 模板預設值），讀完後在 Obsidian 裡手動改為 status: read。Dataview 查詢只顯示 status = "to-read" 的筆記，等於有一個永遠同步的「未讀清單」，完全不需要手動維護。

進階選取模式：只剪藏你真正需要的部分

Web Clipper 提供三種不同粒度的內容擷取模式，根據剪藏目的選擇正確的模式 可以讓筆記更乾淨、更容易回顧：

  • 全文模式（Article）：Clipper 用 Mozilla Readability 解析頁面， 去除導航欄、廣告和側欄，只保留文章主體。適合技術教學文章、部落格長文。
  • 選取文字模式（Selection）：在頁面上先用滑鼠選取要剪藏的段落， 再點擊 Clipper——只有選取的文字會進入 {{content}}。 適合只需要某個程式碼片段、某段論述或某個定義，不需要全文的場景。
  • 高亮彙整模式（Highlights）：閱讀時在多處點擊高亮按鈕標記重點， 最後執行剪藏時，所有高亮段落彙整到 {{highlights}} 變數。 適合需要「精選重點」的閱讀流程，剪藏後不需要再整理。

組合使用策略：建立一個「快速剪藏模板」只有 frontmatter + {{content}}，和一個「精讀模板」同時包含 {{highlights}}、AI 摘要和全文。平時看到感興趣的文章用快速模板一鍵剪藏，深入研究某篇文章時切換到精讀模板，兼顧效率與品質。

模板 JSON 匯出與版本控制

精心設計好的模板是知識管理系統的核心資產。Web Clipper 支援將模板匯出為 JSON 格式， 這讓模板可以：備份到 Vault 的 .obsidian/ 目錄一起被 Git 版本控制、 在不同裝置上同步、與團隊成員分享。 

// 在 Web Clipper 設定頁面，點擊「Templates」→ 選擇模板 → 點右上角「…」→「Export template」
// 會匯出 .json 檔案，可以直接分享或版本控制

// 匯入流程
// 1. 點擊「Templates」頁籤右上角的「Import」按鈕
// 2. 拖入 .json 檔案或複製 JSON 內容貼入
// 3. 模板立即生效，包含所有變數與觸發規則

// 推薦備份路徑（與 Vault 一起版本控制）
vault/
  .obsidian/
    clipper-templates/
      tech-article.json
      youtube-video.json
      academic-paper.json

社群模板庫：Obsidian 官方 GitHub（github.com/obsidianmd/obsidian-clipper）的 templates/ 目錄有來自社群的現成模板，涵蓋 GitHub 倉庫剪藏、Twitter/X 貼文剪藏、Reddit 討論串剪藏等場景，可以直接 import 使用或作為設計起點。

本章小結

本章介紹了讓 Web Clipper 從「存檔工具」進化為「智慧整理工具」的四個進階功能： AI 解釋器（即時生成摘要）、模板觸發器（自動套用對應模板）、 高亮同步（邊讀邊標記）、沉浸式翻譯組合技。 搭配針對中文平台的 obsidian-clipper-cn，幾乎所有常見的資訊來源都能高品質地進入 Vault。

進一步，本章補強了 Handlebars 進階語法（條件渲染與陣列迭代）、 Schema Interpreter（AI 自動萃取結構化 frontmatter properties）、 以及 Clipper + Dataview 整合（剪藏即建立動態閱讀清單）。 這三個進階技巧是把 Web Clipper 從「被動收集」升級為「主動組織」的關鍵。

下一章我們進入更大的主題——如何把 Claude Code 與 Obsidian 深度整合， 讓 AI 直接在你的 Vault 裡操作筆記、建立連結、生成摘要， 把你的知識庫打造成真正意義上的 AI 第二大腦。
